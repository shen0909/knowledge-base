CHAPTER 1

Stream 基础概念

多次的 Future

Future vs Stream

Future 是"一次性的异步结果"，Stream 是"持续的异步数据序列"。两者都建立在事件循环之上，区别只在于数据次数。

Future<T>

  • 异步，返回一个值
  • 只完成一次（成功或失败）
  • 典型场景：网络请求、读文件
  • await 等待结果

Stream<T>

  • 异步，持续发出多个值
  • 可以发出 0 到 N 个数据，最终关闭
  • 典型场景：计时器、位置更新、WebSocket
  • listen() 或 await for 接收
与事件循环的关系：Stream 的每一个事件本质上就是 Event Queue 里的一个回调。stream.listen(callback) 相当于注册了一个持续接收 Event 的监听器。

Stream 的三种创建方式

// 方式一：从已有集合创建（立刻发完所有数据，然后关闭）
final stream = Stream.fromIterable([1, 2, 3]);

// 方式二：周期性发出事件（持续，不会自动关闭）
// 每秒发出一个递增数字，count 从 0 开始
final stream = Stream.periodic(
  const Duration(seconds: 1),
  (count) => count,
);

// 方式三：通过 StreamController 手动控制（最常用）
final controller = StreamController<String>();
controller.add('消息一');
controller.add('消息二');
controller.close(); // 关闭后 listener 会收到 done 事件

执行顺序：同步代码先于 Stream 回调

void main() {
  final stream = Stream.fromIterable([1, 2, 3]);

  stream.listen((value) {
    print(value); // 进入 Event Queue
  });

  print('done'); // 同步，先执行
}

// 输出：done → 1 → 2 → 3

stream.listen() 只是登记回调，不会阻塞。print('done') 是同步代码，先执行完毕，三个数值的回调再从 Event Queue 依次取出执行。

await for：用同步风格消费 Stream

// await for 会等 Stream 关闭后才继续执行后面的代码
Future<void> processStream() async {
  final stream = Stream.fromIterable([1, 2, 3]);

  await for (final value in stream) {
    print(value); // 依次收到 1, 2, 3
  }

  print('Stream 已关闭，继续执行'); // Stream.close() 后才到这里
}

// 注意：对无限 Stream（如 Stream.periodic）使用 await for
// 会导致后面的代码永远无法执行，需要配合 break 或 take()
CHAPTER 2

StreamController

手动控制数据流的水龙头

基本用法

StreamController 是 Stream 的生产端——你决定什么时候往里放数据、什么时候关闭。

// 创建控制器（水龙头）
final controller = StreamController<String>();

// 消费端：监听 Stream（水管出口）
controller.stream.listen(
  (data) => print('收到：$data'),
  onError: (error) => print('出错：$error'),
  onDone: () => print('Stream 已关闭'),
);

// 生产端：往 Stream 里放数据
controller.add('第一条');
controller.add('第二条');
controller.addError(Exception('出了个错'));
controller.add('第三条');

// 关闭 Stream（触发 onDone 回调）
await controller.close();

单订阅 vs 广播 Stream

这是 Stream 最重要的概念区分，踩过才知道有多坑。

特性单订阅（默认）广播（broadcast）
监听者数量只能有 一个 listener
第二个 listen() 直接报错		可以有 任意多个 listener
无 listener 时的数据缓存起来，listener 注册后立即发出直接丢弃，永远收不到
典型用途文件读取、HTTP 响应（一对一）事件总线、BLoC 状态流（一对多）
创建方式StreamController()StreamController.broadcast()
// ❌ 单订阅 Stream 第二次 listen 会报错
final controller = StreamController<String>();
controller.stream.listen((d) => print('A: $d'));
controller.stream.listen((d) => print('B: $d')); // 抛出异常！
// Bad state: Stream has already been listened to.

// ✅ 广播 Stream 支持多个 listener
final controller = StreamController<String>.broadcast();
controller.stream.listen((d) => print('A: $d'));
controller.stream.listen((d) => print('B: $d')); // 正常

controller.add('你好');
// 输出：A: 你好
//       B: 你好
广播 Stream 的数据丢失陷阱：在 listener 注册之前 add() 的数据会直接丢弃。常见场景：用广播 Stream 做事件总线，事件在页面 initState 之前就发出了，页面永远收不到。 
final controller = StreamController<String>.broadcast();

controller.add('消息A'); // ← 此时没有 listener，直接丢弃

controller.stream.listen((d) => print(d)); // 此时才注册

controller.add('消息B'); // ← 有 listener，正常收到

// 只打印：消息B
CHAPTER 3

StreamSubscription

订阅的生命周期管理

listen() 返回的是 StreamSubscription

stream.listen() 返回一个 StreamSubscription 对象，用它来管理这次订阅的生命周期。

final StreamSubscription<int> subscription = stream.listen(
  (data) => print(data),
);

// 暂停接收（数据在单订阅 Stream 中会缓存）
subscription.pause();

// 恢复接收
subscription.resume();

// 取消订阅（必须在 dispose 里调用，否则内存泄漏）
await subscription.cancel();
内存泄漏：如果不调用 cancel()，Stream 的回调会持续持有 Widget 的引用，即使 Widget 已经被销毁，导致内存泄漏甚至 setState() called after dispose() 崩溃。

在 StatefulWidget 里安全使用的标准写法

class _MyState extends State<MyWidget> {
  StreamSubscription<String>? _subscription;
  String _value = '';

  @override
  void initState() {
    super.initState();
    _subscription = myStream.listen((data) {
      if (!mounted) return; // 安全检查
      setState(() => _value = data);
    });
  }

  @override
  void dispose() {
    _subscription?.cancel(); // 必须取消！
    super.dispose();
  }
}

pause / resume：来自你的项目 TimeBloc

你的 TimeBloc 里用了 StreamSubscription 的 pause() 和 resume()，这是一个真实的生产级用法：

// 来自 time_bloc.dart（你的项目）
class TimeBloc extends Bloc<TimerEvent, TimerState> {
  StreamSubscription<int>? _tickerSubscription;

  // 生成计时 Stream：每秒发出一个递减数字，共发 duration 次
  Stream<int> _ticker(int duration) {
    return Stream.periodic(
      const Duration(seconds: 1),
      (x) => duration - x - 1,
    ).take(duration); // take(n)：只取前 n 个数据，然后自动关闭
  }

  void _onStarted(TimerStarted event, Emitter<TimerState> emit) {
    emit(TimerRunning(event.duration));
    _tickerSubscription?.cancel(); // 先取消旧的订阅
    _tickerSubscription = _ticker(event.duration).listen(
      (duration) => add(TimerTicked(duration)), // 每秒发一个事件给 Bloc
    );
  }

  void _onPaused(TimerPaused event, Emitter<TimerState> emit) {
    emit(TimerPausedState(state.duration));
    _tickerSubscription?.pause(); // 暂停 Stream，不取消
  }

  void _onResumed(TimerResumed event, Emitter<TimerState> emit) {
    emit(TimerRunning(state.duration));
    _tickerSubscription?.resume(); // 恢复接收
  }

  @override
  Future<void> close() {
    _tickerSubscription?.cancel(); // Bloc 销毁时取消订阅
    return super.close();
  }
}
关键设计：pause() 不会丢弃数据（单订阅 Stream 会缓存），cancel() 才会彻底终止。计时器暂停用 pause()，页面销毁或重置用 cancel()。
CHAPTER 4

StreamBuilder

把 Stream 和 UI 连接起来

StreamBuilder 封装了什么

手动把 Stream 连接到 UI 需要写固定模板：initState 里 listen，回调里 setState，dispose 里 cancel。StreamBuilder 把这套模板封装好了。

手动写（冗长）

  • initState 里 listen
  • 回调里 setState
  • dispose 里 cancel
  • mounted 检查
  • 共约 20 行模板代码

StreamBuilder（简洁）

  • 自动管理 subscribe / unsubscribe
  • 数据变化自动重建 UI
  • 内置 ConnectionState 状态机
  • stream 变化时自动切换订阅
StreamBuilder<int>(
  stream: myStream,
  initialData: 0, // 可选：Stream 还没发数据时的初始值
  builder: (context, AsyncSnapshot<int> snapshot) {
    switch (snapshot.connectionState) {
      case ConnectionState.waiting:
        return const CircularProgressIndicator();
      case ConnectionState.active:
        return Text('当前值：${snapshot.data}');
      case ConnectionState.done:
        return Text('Stream 已结束，最后值：${snapshot.data}');
      case ConnectionState.none:
        return const Text('没有 Stream');
    }
  },
)

AsyncSnapshot 的四种状态

ConnectionState含义snapshot.data
nonestream 参数为 nullnull 或 initialData
waiting已连接 Stream，还没收到任何数据null 或 initialData
active正在接收数据（每次新数据到来都是此状态）最新的数据值
doneStream 已关闭（controller.close() 之后）最后一次收到的数据
注意：页面刚打开时，Stream.periodic 第一个事件还没到，snapshot.connectionState 是 waiting，snapshot.data 是 null（除非设置了 initialData）。直接使用 snapshot.data 而不判断状态会导致 null 崩溃。 
// ❌ 危险写法：snapshot.data 可能为 null
Text('${snapshot.data}') // 显示 "null"

// ✅ 安全写法一：设置 initialData
StreamBuilder<int>(
  stream: myStream,
  initialData: 0,
  builder: (context, snapshot) => Text('${snapshot.data}'),
)

// ✅ 安全写法二：判断 connectionState
if (snapshot.connectionState == ConnectionState.waiting) {
  return const CircularProgressIndicator();
}
return Text('${snapshot.data ?? 0}');
CHAPTER 5

BLoC 源码透视

用 Stream 眼光重新看 BLoC

BlocBase 的核心：两个 StreamController

每一个 Bloc / Cubit 的底层，都持有两个广播 StreamController：

// flutter_bloc 源码（简化）
abstract class BlocBase<State> {
  // 状态流：对外暴露，BlocBuilder / context.watch 监听的就是这个
  final _stateController = StreamController<State>.broadcast();

  // 事件流（仅 Bloc 有，Cubit 没有）：接收外部 add() 进来的事件
  final _eventController = StreamController<Event>.broadcast();

  Stream<State> get stream => _stateController.stream;

  // emit() 本质就是往状态 Stream 里 add 一个新状态
  void emit(State state) {
    if (_stateController.isClosed) return;
    _state = state;
    _stateController.add(state); // ← 核心就是这一行
  }

  // Bloc 销毁时关闭两个 StreamController
  Future<void> close() async {
    await _stateController.close();
    await _eventController.close();
  }
}
为什么用广播 Stream？因为同一个 Bloc 可能被多个 BlocBuilder、BlocListener 同时监听。单订阅 Stream 只允许一个 listener，必须用广播。

emit() 到 UI 更新的完整链路

用户点击按钮 context.read<CalculateBloc>().add(Increment()) ↓ Bloc 内部 Increment 事件进入 _eventController（事件 Stream） on<Increment> 的处理函数被调用 执行：emit(CalculateState(state.count + 1)) ↓ emit() 调用 _stateController.add(newState) 新状态进入状态 Stream（广播） ↓ 所有监听者收到通知 BlocBuilder 的 StreamSubscription 回调触发 → 内部调用 setState() → markNeedsBuild() → scheduleFrame() ↓ vsync 到来 → Build Phase → UI 更新

BlocBuilder 本质是 StreamBuilder

// 你写的
BlocBuilder<CalculateBloc, CalculateState>(
  builder: (context, state) => Text('${state.count}'),
)

// 它底层做的事（简化）
StreamBuilder<CalculateState>(
  stream: context.read<CalculateBloc>().stream, // 广播 Stream
  builder: (context, snapshot) {
    final state = snapshot.data ?? bloc.state;
    return Text('${state.count}');
  },
)

// buildWhen 对应 Stream 的 where() 过滤
BlocBuilder<MyBloc, MyState>(
  buildWhen: (prev, curr) => prev.count != curr.count,
  // 相当于：bloc.stream.where((s) => prev.count != s.count)
  builder: (context, state) => Text('${state.count}'),
)

BlocListener 本质是 StreamSubscription

// 你写的（来自 time_one.dart）
BlocListener<TimeBloc, TimerState>(
  listener: (context, state) {
    if (state is TimerFinished) {
      ScaffoldMessenger.of(context).showSnackBar(...);
    }
  },
  child: ...,
)

// 底层做的事（简化）
// 在 initState 里订阅
_subscription = bloc.stream.listen((state) {
  if (state is TimerFinished) {
    ScaffoldMessenger.of(context).showSnackBar(...);
  }
});

// 在 dispose 里取消
_subscription?.cancel();
BlocListener vs BlocBuilder 的本质区别：
BlocListener 是纯 listen()，只触发副作用（弹窗、跳转），不重建 UI。
BlocBuilder 是 StreamBuilder，每次收到新状态都调用 setState()，重建 UI。

on<Event> 本质是 Stream 事件监听

你的 CalculateBloc 里的 on<Increment>，底层是在事件 Stream 上注册了一个过滤监听：

// 你写的（calculate_bloc.dart）
CalculateBloc() : super(CalculateState(0)) {
  on<Increment>((event, emit) {
    emit(CalculateState(state.count + 1));
  });
  on<Decrement>((event, emit) {
    emit(CalculateState(state.count - 1));
  });
}

// 底层做的事（简化）
_eventController.stream
  .where((event) => event is Increment) // 只处理 Increment 事件
  .listen((event) {
    emit(CalculateState(state.count + 1));
  });

_eventController.stream
  .where((event) => event is Decrement)
  .listen((event) {
    emit(CalculateState(state.count - 1));
  });

BLoC 完整架构：Stream 视角

外部（UI） bloc.add(Increment()) ↓ 进入 事件 Stream（StreamController.broadcast） _eventController.stream ↓ on<Increment> 过滤并处理 Bloc 内部逻辑 执行业务逻辑 emit(newState) → _stateController.add(newState) ↓ 进入 状态 Stream（StreamController.broadcast） bloc.stream ↓ 多个监听者同时收到 ┌─────────────────────────────────────────┐ │ BlocBuilder → StreamBuilder → setState │ ← 更新 UI │ BlocListener → listen → 副作用回调 │ ← 弹窗/跳转 │ context.watch → dependOnInherited... │ ← 精准重建 └─────────────────────────────────────────┘
一句话总结：BLoC 就是两个广播 StreamController 的封装——一个接收事件，一个发出状态。add() 往事件流里 push，emit() 往状态流里 push，UI 层监听状态流自动更新。

CHAPTER 6

Stream / StreamController / StreamSubscription 三者关系

全景梳理

一句话定位三者职责

对象角色类比
StreamController数据的生产端，控制数据何时进入管道水龙头（你控制开关）
Stream数据的定义与通道，本身是惰性的，没有人监听时什么都不发生水管（通道本身）
StreamSubscription一次订阅关系的容器，持有回调，控制订阅生命周期打开水龙头后流出的水（激活的连接）

listen() 调用时发生了什么

这句话是正确的："Stream 在被订阅时，会创建 StreamSubscription，并将 onData 等回调传给 StreamSubscription。"

完整过程如下：

stream.listen(onData, onError: onError, onDone: onDone) ↓ Stream 内部创建一个 StreamSubscription 对象 ↓ 把三个回调存入 StreamSubscription： ├── onData → 每次收到新数据时调用 ├── onError → 收到错误时调用 └── onDone → Stream 关闭时调用一次 ↓ StreamSubscription 返回给调用方 ↓ 数据流激活——后续 controller.add() 的数据 会触发 StreamSubscription 内部的 onData 回调
Stream 是惰性的：在 listen() 被调用之前，Stream 只是一个定义，什么都不会发生。listen() 这个动作才真正激活了数据流，创建了 StreamSubscription，数据才开始流动。

三者完整关系图

StreamController<T> ├── .sink 生产端入口 │ └── sink.add(data) / sink.addError() / sink.close() └── .stream Stream 对象（消费端出口） │ │ .listen(onData, onError, onDone) ↓ StreamSubscription<T>（一次订阅的容器） ├── 存储回调：onData / onError / onDone ├── pause() 暂停接收（单订阅会缓存数据） ├── resume() 恢复接收 └── cancel() 彻底取消，释放资源 controller.add(data) ↓ Stream 内部把 data 路由给所有活跃的 StreamSubscription ↓ 每个 StreamSubscription 的 onData 回调被调用 ↓（对 Flutter 而言） 回调里的 setState() → markNeedsBuild() → scheduleFrame() ↓ vsync 到来 → Build Phase → UI 更新

为什么 Stream 本身不持有数据

Stream 只是"数据通道的定义"，它不缓存数据，不持有状态。真正缓存和路由数据的是 StreamController 内部的实现。

这个设计的好处：同一个 Stream 对象可以被多次描述、组合、变换（.map() / .where() / .take()），每次都产生新的 Stream 定义，直到有人 listen() 才真正激活执行。

final controller = StreamController<int>.broadcast();

// 这三行只是在"描述"数据流，还没有任何执行
final doubled = controller.stream.map((x) => x * 2);
final evenOnly = doubled.where((x) => x % 2 == 0);
final first3 = evenOnly.take(3);

// listen() 才真正激活整条链
first3.listen((v) => print(v));

// 现在 add() 的数据才会经过 map → where → take → onData
controller.add(1); // 2，偶数，通过
controller.add(2); // 4，偶数，通过
controller.add(3); // 6，偶数，通过（take(3) 后自动结束）
CHAPTER 7

async* 与 yield

用函数语法创建 Stream

基本语法

async* 把一个函数标记为"异步生成器"，该函数的返回类型是 Stream<T>。yield 向 Stream 发出一个值，然后暂停，等待下一次被消费。

// async* 函数：返回 Stream，每次 yield 发出一个值
Stream<int> countDown(int from) async* {
  for (int i = from; i >= 0; i--) {
    await Future.delayed(const Duration(seconds: 1));
    yield i; // 发出当前值，函数在这里"暂停"
             // 等消费者准备好后，才继续执行下一次循环
  }
  // 函数执行结束，Stream 自动关闭（onDone 触发）
}

// 使用
countDown(3).listen((v) => print(v));
// 每秒输出：3 → 2 → 1 → 0，然后 onDone 触发

yield* ：委托给另一个 Stream / Iterable

yield* 把另一个 Stream 或 Iterable 的所有值依次转发出去，相当于"展开"。

Stream<int> combined() async* {
  yield* countDown(3); // 先把 3→2→1→0 全部发出
  yield* countDown(2); // 再把 2→1→0 全部发出
  yield 99;            // 最后发一个额外的值
}
// 输出：3 2 1 0 2 1 0 99

与 StreamController 的对比：拉模型 vs 推模型

async* / yield（拉模型）

  • 每次 yield 后函数暂停
  • 等消费者消费完才继续
  • 数据生产和消费节奏自然同步
  • 适合：顺序生成、有规律的数据序列
  • 函数结束 Stream 自动关闭

StreamController（推模型）

  • 随时可以 add()，不管消费者
  • 广播模式下无人监听则数据丢失
  • 适合：外部事件驱动（用户操作、网络）
  • 需要手动 close()
  • BLoC 用的就是这种

改写 TimeBloc 的 _ticker

你的项目里 TimeBloc._ticker 用 Stream.periodic 实现，用 async* 改写是完全等价的，且更直观：

// 原写法（Stream.periodic + take）
Stream<int> _ticker(int duration) {
  return Stream.periodic(
    const Duration(seconds: 1),
    (x) => duration - x - 1,
  ).take(duration);
}

// 等价的 async* 写法（逻辑更清晰）
Stream<int> _ticker(int duration) async* {
  for (int i = duration - 1; i >= 0; i--) {
    await Future.delayed(const Duration(seconds: 1));
    yield i; // 每秒发出一个递减数字
  }
  // 循环结束，Stream 自动关闭，_tickerSubscription 收到 onDone
}
两种写法在行为上完全一致，选哪个取决于可读性偏好。async* 更接近普通代码的写法，Stream.periodic 更函数式。

async* 与事件循环的关系

async* 函数里的 await 和普通 async 函数一样——遇到 await 主线程不会阻塞，把后续逻辑注册到事件循环，等待信号回来再继续。

countDown(3).listen(onData) ↓ Stream 被激活，函数开始执行 i = 3 await Future.delayed(1s) → 主线程返回事件循环（不阻塞） 1秒后回调进 Event Queue → 继续执行 yield 3 → 触发 onData(3)，函数暂停 ↓ 消费者处理完毕，函数继续 i = 2 await Future.delayed(1s) → 主线程返回事件循环 ... yield 0 → 触发 onData(0)，函数暂停 ↓ 循环结束，函数 return Stream 自动关闭 → 触发 onDone
