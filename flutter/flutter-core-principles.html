Flutter 架构三层

全局鸟瞰

三层架构概览

Framework (Dart) — 用户代码 + 所有 Widget + Material/Cupertino
widgets / rendering / animation / gestures / services
Engine (C++) — Skia/Impeller 渲染、Dart VM、文字排版
Dart Runtime · Skia / Impeller · Text Layout · Platform Channels
Embedder — Android / iOS / Desktop / Web 原生壳
提供 Surface · 事件循环 · 线程 · 平台 API

关键设计决策

  • 自绘每一个像素 — 不调用原生控件，跨平台像素级一致
  • Dart AOT 编译 — Release 模式原生机器码，无 JIT 解释开销
  • Impeller（新渲染器） — 预编译着色器，消除卡顿
  • 单线程 UI — Dart 主 Isolate 驱动，靠 async 而非多线程

与 RN / WebView 方案对比

  • React Native — JS Bridge 调用原生组件，有跨层通信开销
  • WebView — 浏览器渲染，性能受限于 Web 引擎
  • Flutter — Engine 直接绘制到 Canvas，零中间层
  • 代价：包体积更大（含 Dart VM + Skia）
记忆口诀：Framework 写逻辑 → Engine 跑 Dart + 渲染 → Embedder 对接系统。 Flutter 的「跨平台」只在 Embedder 层适配，上面两层完全共享。
MENTAL MODEL

两大基石：理解所有 Flutter 问题的最高层框架

核心观点

Flutter 所有问题归根到底可以分为两类：界面是什么（三棵树） 和 代码何时执行（事件循环）。 这两者不是独立的，而是通过 SchedulerBinding 紧密咬合在一起。

基石一：三棵树

  • Widget / Element / RenderObject
  • → 渲染管线（Build → Layout → Paint）
  • → 状态管理（InheritedWidget / Provider）
  • → 路由 / Overlay / Key
  • 解释所有 UI 与布局问题

基石二：事件循环

  • MicroTask Queue / Event Queue
  • → async / await / Future / Stream
  • → Isolate（真正的并行）
  • → Platform Channel（跨线程通信）
  • 解释所有代码执行问题

SchedulerBinding — 两大基石的桥梁

这是最常被忽略、但最关键的连接机制。setState() 并不是"立刻重建"， 而是通过 SchedulerBinding 把渲染任务挂在事件循环的 vsync 节拍上。

用户交互 / setState() 触发状态变化
↓
markNeedsBuild() 标记 Element dirty，不立即重建
↓
scheduleFrame() SchedulerBinding：向事件循环注册帧回调
↓
事件循环等待 vsync（≈16ms） GPU 时钟信号驱动，不是 Timer
↓
Build → Layout → Paint → Composite 完整渲染管线执行
关键结论：同一帧内无论调用多少次 setState()， Flutter 只执行一次渲染管线（批量合并）。这正是 SchedulerBinding 的价值： 把"任意时刻的标记"统一压缩到"下一个 vsync 帧"里执行。

手势 / 输入系统 — 第三个驱动源

三棵树描述"界面是什么"，事件循环描述"代码何时执行"， 但"用户如何触发状态变化"是一个独立的驱动源，需要单独理解。

原生触摸事件（Embedder 层）
↓
GestureBinding — HitTest 从根向下遍历，收集命中的 RenderObject
↓
GestureArena 竞争 多个 Recognizer 竞争，最终 accept() 一个
↓
onTap / onPan 回调 回调里调用 setState() → 回到三棵树流程
三者关系：手势系统是"触发器"，三棵树是"描述器"， 事件循环是"调度器"。手势产生 setState → SchedulerBinding 调度帧 → 三棵树重建渲染。 Flutter 里一个点击事件走完整个链路就是这三者协作的体现。

完整心智模型图

三棵树（界面描述） Widget → Element → RenderObject │ markNeedsBuild / markNeedsLayout / markNeedsPaint ▼ SchedulerBinding（两大基石的桥） scheduleFrame() → 向事件循环注册 vsync 回调 │ ▼ Dart 事件循环（代码调度） MicroTask Queue ← scheduleMicrotask() / Future.then Event Queue ← Timer / I-O / vsync 帧回调 │ vsync 触发 ▼ Build Phase → Layout Phase → Paint Phase → Composite（上屏） ▲ │ setState() / notifyListeners() / stream event 手势 / 输入系统（驱动源） Embedder 触摸事件 → GestureBinding → HitTest → Arena → 回调

Binding 体系 — runApp() 做了什么

Flutter 启动时，WidgetsFlutterBinding.ensureInitialized() 把一组 Mixin 组合成全局单例， 每个 Binding 负责系统的一个子模块，共同驱动整个 Flutter 运行时。

// Flutter 框架源码（简化）
class WidgetsFlutterBinding extends BindingBase with
  GestureBinding,    // 手势 HitTest + Arena
  SchedulerBinding,  // vsync 帧调度（两大基石的桥）
  ServicesBinding,   // Platform Channel + 键盘事件
  PaintingBinding,   // 图片缓存 ImageCache
  SemanticsBinding,  // 无障碍语义树
  RendererBinding,   // RenderObject 树管理
  WidgetsBinding {}  // Widget/Element 树 + BuildOwner

void main() {
  WidgetsFlutterBinding.ensureInitialized(); // 初始化所有 Binding
  runApp(MyApp()); // 把根 Widget 挂载到 Element 树
}

各 Binding 职责速查

  • GestureBinding：接收 Embedder 触摸事件 → HitTest → Arena
  • SchedulerBinding：vsync 注册、帧回调队列（transient/persistent/post）
  • ServicesBinding：Platform Channel 消息路由
  • RendererBinding：持有 RenderView（根 RenderObject）
  • WidgetsBinding：持有 BuildOwner，驱动 Element 的 build/update

三类帧回调（SchedulerBinding）

  • transientCallbacks：每帧执行一次，用完即移除（AnimationController 用此）
  • persistentCallbacks：每帧都执行，不移除（RendererBinding 用此驱动渲染管线）
  • postFrameCallbacks：当前帧结束后执行一次（addPostFrameCallback）

CHAPTER 1

三棵树

Flutter 最核心的设计
树类型生命周期职责
Widget 树不可变配置（const）频繁重建，极轻量描述"长什么样"
Element 树可变运行时实例尽量复用，持久存在连接 Widget ↔ RenderObject，持有 State
RenderObject 树布局+绘制对象重量级，最大化复用测量、布局、绘制

Widget 类型层次（理解"为什么这样设计"的前提）

Widget — 所有 Widget 的基类，不可变配置
StatelessWidget — 无状态，build() 是纯函数 StatefulWidget — 有状态，配套 State 对象持有可变数据 RenderObjectWidget — 直接创建/更新 RenderObject，是叶子渲染节点
LeafRenderObjectWidget — 无子节点（如 RawImage、Texture） SingleChildRenderObjectWidget — 单子节点（如 Padding、Align、SizedBox） MultiChildRenderObjectWidget — 多子节点（如 Row、Stack、Flex）
ProxyWidget — 不渲染，透传子 Widget，主要用于数据传递
InheritedWidget — 向下广播数据（Theme、MediaQuery、Provider 的基础） ParentDataWidget — 向父 RenderObject 传递布局数据（如 Positioned、Flexible）
关键规律：StatelessWidget / StatefulWidget 最终都会在 build() 里返回 RenderObjectWidget（或其嵌套组合），才能真正产生 RenderObject 参与布局绘制。 InheritedWidget 和 ParentDataWidget 不自己渲染，只负责"传递信息"。

三棵树并排可视化

四种典型 Widget 在三棵树中的对应关系。虚线 = 同一节点的跨树映射；箭头 = 父子关系。

三棵树协作流程

build() 返回新 Widget 树 ↓ Element.updateChild() — 对比新旧 Widget 同类型同位置 → 复用 Element，调用 element.update(newWidget) 类型变了 → 销毁旧 Element + RenderObject，创建新的 ↓ element.updateRenderObject() — 把新 Widget 的配置同步到 RenderObject ↓ RenderObject.markNeedsLayout() / markNeedsPaint()

Widget rebuild ≠ Element rebuild

  • 调用 setState() → 当前 Element 标记 dirty
  • build() 返回新 Widget 树（廉价）
  • Element 树对比新旧 Widget，决定复用/重建
  • 只有类型/Key 变化才销毁 Element
  • RenderObject 更新属性，不重建

关键方法调用链

  • Widget.createElement() → 创建对应 Element
  • Element.mount() → 插入 Element 树
  • RenderObjectElement.createRenderObject()
  • RenderObjectElement.updateRenderObject()
  • State.build(context) → 返回子 Widget
常见误解：setState() 不会重建整棵树，只重建从当前 Element 向下的子树。 Flutter 的 diff 算法保证 RenderObject 层面的最小化更新。

StatefulWidget 三棵树完整示例

以下代码展示一次 setState() 如何经过三棵树各自的职责，最终产生一帧渲染。 

// ① Widget 树（不可变配置，描述"长什么样"）
class CounterWidget extends StatefulWidget {
  const CounterWidget({super.key});           // const：引用相等时 diff 可跳过
  @override
  State createState() => _CounterState(); // ② 创建 State
}

// ② Element 树（运行时）：StatefulElement 持有 State，持久存在
// ③ State 持有可变数据
class _CounterState extends State {
  int _count = 0;

  @override
  void initState() {              // Element.mount() 后调用，只触发一次
    super.initState();
  }

  void _increment() {
    setState(() {                 // → markNeedsBuild() → scheduleFrame()
      _count++;                   //   下一个 vsync 触发 build()
    });
  }

  @override
  Widget build(BuildContext context) { // context 就是 StatefulElement 本身
    return GestureDetector(
      onTap: _increment,
      child: Text('$_count'),     // ← Text 是 LeafRenderObjectWidget
    );                            //   对应的 RenderParagraph 做布局+绘制
  }

  @override
  void dispose() {                // Element unmount 时调用，释放资源
    super.dispose();
  }
}

// 三棵树对应关系：
// Widget:        CounterWidget → GestureDetector → Text('0')
// Element:       StatefulElement → GestureDetectorElement → RenderObjectElement
// RenderObject:  （无）           → （无）                → RenderParagraph
//                ↑ ProxyWidget 类 Widget 不产生独立 RenderObject

const Widget — 零成本的性能优化

const 是 Flutter 里最廉价的性能优化，利用的是 Dart 编译期常量和 Element diff 的引用相等快捷路径。

❌ 没有 const

// 父 setState() 每次都 new Icon()
// Element diff 看到"新对象" → 调用 update()
// RenderObject 重新设置属性
build() => Icon(Icons.home); // 每帧 new

✅ 加上 const

// Dart 编译期创建唯一实例
// Element diff: old.widget == new.widget（引用相等）
// → 直接跳过，不调用 updateRenderObject()
build() => const Icon(Icons.home); // 同一对象
规则：Widget 的所有字段都是编译期常量时，加 const。 静态 UI 部分（图标、标题、分割线）全部加 const，父组件 rebuild 时这些子树完全不动。

BuildContext 与 Element

context 本质是什么
核心结论：BuildContext 是一个接口，Element 是它的唯一实现。 你拿到的 context 就是当前 Widget 在 Element 树上的节点。 
// Flutter 源码（简化）
abstract class Element implements BuildContext {
  Element? _parent;           // 父节点指针
  Widget _widget;             // 持有对应的 Widget 配置
  Map<Type, InheritedElement>? _inheritedWidgets; // InheritedWidget 查找表
  bool _active = false;       // 是否在树上（mounted）
}

两种祖先查找机制对比

方法方向复杂度响应式依赖典型用途
findAncestorStateOfType<T>() 沿 _parent 链向上 O(n) ❌ 无 Scaffold.of(context)
dependOnInheritedWidgetOfExactType<T>() 查 _inheritedWidgets Map O(1) ✅ 有，自动重建 Theme.of, MediaQuery.of
关键约束：两种方式都只能向上找祖先，不能向下找子孙。 这决定了 InheritedWidget 只能向下传数据，以及 Overlay.of() 对 context 的要求。

❌ context 失效的场景

  • widget 被 dispose，element 从树上移除
  • async 操作后，widget 已经 pop
  • GlobalKey 指向的 widget 被 Get.offAll() 替换
  • initState 里同步读 InheritedWidget（还未 mount 完成）

✅ context 安全使用规则

  • async await 后先 if (!mounted) return
  • InheritedWidget 在 didChangeDependencies 或 build 里读
  • 导航 pop 前先保存好 context 引用再调用 API
  • GlobalKey 只挂在生命周期与 App 等长的 widget

didUpdateWidget — 最容易被误用的回调

父组件重建时，如果传给子组件的 widget 对象变了（但类型相同），Flutter 复用 Element 并调用 didUpdateWidget(oldWidget)。这是检测"外部配置变化"、重新订阅资源的正确时机。 

class PlayerWidget extends StatefulWidget {
  final AnimationController controller; // 父组件可能传入新的 controller
  const PlayerWidget({required this.controller, super.key});
  @override
  State createState() => _PlayerWidgetState();
}

class _PlayerWidgetState extends State {
  @override
  void initState() {
    super.initState();
    widget.controller.addListener(_onChanged); // 首次订阅
  }

  @override
  void didUpdateWidget(PlayerWidget oldWidget) {
    super.didUpdateWidget(oldWidget);
    // 父组件传入了新的 controller → 必须重新订阅！
    if (widget.controller != oldWidget.controller) {
      oldWidget.controller.removeListener(_onChanged); // 取消旧订阅
      widget.controller.addListener(_onChanged);       // 建立新订阅
    }
  }

  void _onChanged() => setState(() {});

  @override
  void dispose() {
    widget.controller.removeListener(_onChanged);
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => /* ... */
    Text('value: ${widget.controller.value}');
}
常见 Bug：忘记在 didUpdateWidget 里处理 controller 替换， 导致监听的还是旧对象，UI 不更新。凡是 widget 持有 Listenable / Stream / Controller， 都应在 didUpdateWidget 里比较新旧并重新订阅。

setState() 的完整工作原理（含 diff 阶段）

setState(() { ... }) ↓ 执行传入的闭包（修改状态变量） ↓ element.markNeedsBuild() — 标记 Element 为 dirty，不立即重建 ↓ SchedulerBinding.scheduleFrame() — 请求下一帧 ↓ Vsync 信号到来 ↓ BuildOwner.buildScope() — 统一 rebuild 所有 dirty elements ↓ State.build(context) — 返回"新 Widget 子树"（廉价，只是配置对象） ↓ ── diff 阶段：Element.updateChild(newWidget) ── 对每个子节点调用 Widget.canUpdate(oldWidget, newWidget) 判断条件：oldWidget.runtimeType == newWidget.runtimeType && oldWidget.key == newWidget.key ↓ 两者都相同（可复用） ↓ 任意一个不同（需重建） element.update(newWidget) element.deactivate() → StatefulElement 调用 → element.unmount()（→ dispose()） didUpdateWidget(oldWidget) newWidget.createElement() → RenderObjectElement 调用 → element.mount() updateRenderObject() → StatefulWidget: createState() → RenderObject 只更新属性，不销毁 → initState() → build() （布局/绘制按需 mark，最小化重绘） → createRenderObject()（新建）
canUpdate 是 diff 的核心判断：runtimeType 变了（如 Text → Icon）或 Key 变了（如 ValueKey(1) → ValueKey(2)），Flutter 就认为"这不是同一个 widget"， 彻底销毁旧 Element + RenderObject，重新走完整的创建生命周期。 这也是 Key 能"保留 State"的底层原因——相同 Key 让 canUpdate 返回 true，Element 被复用，State 随之保留。

源码级完整流程：从 setState() 到像素更新

每一步都对应 Flutter framework 里真实存在的方法，以下源码均来自 packages/flutter/lib/src/widgets/framework.dart，已精简非核心代码。

第一步：setState() — 标记 dirty，预约下一帧

// State.setState()（framework.dart）
void setState(VoidCallback fn) {
  fn();                        // ① 执行你传入的闭包，修改数据
  _element!.markNeedsBuild();  // ② 通知对应的 Element：你脏了
}

// Element.markNeedsBuild()
void markNeedsBuild() {
  _dirty = true;                    // 打上 dirty 标记
  owner!.scheduleBuildFor(this);    // 把自己加入 BuildOwner 的 dirty 列表
  // scheduleBuildFor 内部会调用 SchedulerBinding.scheduleFrame()
  // 向系统预约下一个 vsync 信号
}
此时什么都没有重建，只是打了个标记。主线程继续处理事件循环里的其他事情。

第二步：BuildOwner.buildScope() — vsync 到来，统一重建

// BuildOwner.buildScope()（framework.dart）
// vsync 信号到来后，WidgetsBinding 调用这个方法
void buildScope(Element context, [VoidCallback? callback]) {
  // _dirtyElements 是所有被 markNeedsBuild() 标记过的 Element 列表
  // 按在树中的深度排序（父节点先重建）
  _dirtyElements.sort(Element._sort);

  int index = 0;
  while (index < _dirtyElements.length) {
    final Element element = _dirtyElements[index];
    element.rebuild();   // 依次触发每个脏 Element 重建
    index++;
  }
  _dirtyElements.clear(); // 重建完毕，清空 dirty 列表
}
同一帧内无论调用多少次 setState()，都只是往 _dirtyElements 里加记录。buildScope() 只跑一次，批量处理所有脏节点——这就是多次 setState() 只渲染一次的根本原因。

第三步：State.build() — 生成新 Widget 子树

// StatefulElement.performRebuild()（framework.dart）
void performRebuild() {
  // 调用你写的 build() 方法，得到一棵新的 Widget 子树
  // Widget 是纯配置对象，new 一个几乎没有成本
  final Widget built = state.build(this);

  // 拿到新 Widget 子树后，进入 diff 阶段
  _child = updateChild(_child, built, slot);
}
build() 返回的是一棵全新的 Widget 树，但这只是"配置描述"，不是真正的 UI。真正决定要不要更新 UI 的是下一步的 diff。

第四步：Element.updateChild() — diff 核心

// Element.updateChild()（framework.dart）
// 对新 Widget 子树里的每个节点，和旧 Element 树的对应位置做比较
Element? updateChild(Element? child, Widget? newWidget, Object? newSlot) {

  // 情况一：新位置没有 Widget → 直接销毁旧 Element
  if (newWidget == null) {
    if (child != null) deactivateChild(child);
    return null;
  }

  if (child != null) {
    // 情况二：新旧 Widget 是同一个对象（const Widget 的引用相等）
    // → 完全跳过，什么都不做，这是 const 优化的底层原理
    if (child.widget == newWidget) {
      return child;
    }

    // 情况三：canUpdate 判断能否复用这个 Element
    if (Widget.canUpdate(child.widget, newWidget)) {
      child.update(newWidget); // 复用，只更新内容
      return child;
    }

    // 情况四：canUpdate 返回 false → 销毁旧 Element，重新创建
    deactivateChild(child); // 触发 deactivate() → dispose()
  }

  // 创建全新的 Element（触发 createElement → mount → initState → build）
  return inflateWidget(newWidget, newSlot);
}

// Widget.canUpdate()（framework.dart）
// 这就是整个 diff 算法的核心判断，只有这两行
static bool canUpdate(Widget oldWidget, Widget newWidget) {
  return oldWidget.runtimeType == newWidget.runtimeType
      && oldWidget.key == newWidget.key;
}
Flutter diff 的本质：不是全树对比，而是同位置逐个判断。判断条件极其简单——只看 runtimeType 和 key，时间复杂度 O(n)。官方称之为 "linear reconciliation"（线性调和）。

第五步：canUpdate = true 时 — 复用 Element，更新 RenderObject

// StatefulElement.update()（framework.dart）
// canUpdate 返回 true，走这条路
void update(StatefulWidget newWidget) {
  super.update(newWidget);
  final StatefulWidget oldWidget = state._widget!;
  state._widget = newWidget;          // State 里的 widget 引用更新为新 Widget
  state.didUpdateWidget(oldWidget);   // 通知 State：你的 widget 配置换了
  rebuild();                          // 重新调用 State.build()
}

// RenderObjectElement.update()（framework.dart）
// 对于 RenderObjectWidget（如 Text、Container），走这条路
void update(covariant RenderObjectWidget newWidget) {
  super.update(newWidget);
  // 把新 Widget 的配置同步到已有的 RenderObject
  // 这里会调用你在 LeafRenderObjectWidget 里写的 updateRenderObject()
  newWidget.updateRenderObject(this, renderObject);
  // updateRenderObject 内部根据哪些属性变了，调用对应的 mark 方法：
  // 只有视觉属性变了 → markNeedsPaint()   （跳过 Layout，最轻）
  // 尺寸相关属性变了 → markNeedsLayout()  （重新 Layout + Paint）
}
关键结论：canUpdate = true 时，RenderObject 不会被销毁重建，只是调用 updateRenderObject() 更新属性。RenderObject 决定自己需要重新 Layout 还是只需要重新 Paint，精确控制开销。

第六步：canUpdate = false 时 — 完整生命周期

// Element.deactivateChild()（framework.dart）
// canUpdate 返回 false，旧 Element 走销毁流程
void deactivateChild(Element child) {
  child.deactivate();   // 暂时移出树（还没彻底销毁）
  owner!.unmountAll();  // 彻底销毁
  // StatefulElement.unmount() 内部调用 state.dispose()
}

// Element.inflateWidget()（framework.dart）
// 然后用新 Widget 创建全新的 Element
Element inflateWidget(Widget newWidget, Object? newSlot) {
  final Element newChild = newWidget.createElement(); // Widget 创建对应 Element
  newChild.mount(this, newSlot);  // 挂载到 Element 树
  // mount 内部：
  //   StatefulElement → createState() → initState() → didChangeDependencies() → build()
  //   RenderObjectElement → createRenderObject() → 创建全新 RenderObject
  return newChild;
}
代价：销毁+重建意味着 State 完全重置，RenderObject 重新创建，走完整生命周期。这就是为什么要用 Key 保证 canUpdate 返回 true——避免不必要的完整重建。

InheritedWidget

数据向下传递的核心机制
InheritedWidget 是 Flutter 数据传递的基础设施。 Theme、MediaQuery、Provider、Navigator 的 overlay 机制，底层全部依赖它。

工作原理（O(1) 查找 + 响应式更新）

InheritedWidget.mount() ↓ 把自己写入子孙所有 element 的 _inheritedWidgets Map key = InheritedWidget 的 runtimeType ↓ 子孙调用 context.dependOnInheritedWidgetOfExactType<MyInherited>() ↓ O(1) 查 Map 找到 InheritedElement ↓ 同时注册依赖：InheritedElement._dependents 记录此 element ↓ InheritedWidget 数据变化 → updateShouldNotify() 返回 true ↓ 遍历 _dependents，逐一调用 element.didChangeDependencies() ↓ 触发 markNeedsBuild() → 依赖者重建
// 实现一个简单的 InheritedWidget
class MyTheme extends InheritedWidget {
  final Color primaryColor;

  const MyTheme({required this.primaryColor, required super.child});

  // 控制是否通知依赖者重建
  @override
  bool updateShouldNotify(MyTheme old) => old.primaryColor != primaryColor;

  // 便捷访问方法
  static MyTheme of(BuildContext context) {
    return context.dependOnInheritedWidgetOfExactType<MyTheme>()!;
  }
}

// 使用
final color = MyTheme.of(context).primaryColor; // O(1)，自动建立依赖

渲染管线

一帧的完整旅程

四个阶段

Vsync 信号（16ms / 60fps） ↓ ① Build Phase SchedulerBinding 收集所有 dirty elements 依次调用 State.build(context) → 生成新 Widget 子树 Element.updateChild() 执行 diff ↓ ② Layout Phase RenderObject.performLayout() Constraints ↓ go down 父传 BoxConstraints 给子 Sizes ↑ go up 子返回自己的 Size Parent sets position 父决定子的偏移位置 ↓ ③ Paint Phase RenderObject.paint(context, offset) 生成 DisplayList → 写入 Layer 树 RepaintBoundary 隔离重绘区域 ↓ ④ Composite Flutter Engine 把 Layer 树发给 GPU Skia / Impeller 合成上屏

渲染管线时序图（一帧 16ms 内发生了什么）

布局约束原则（最重要的布局心智模型）

  • 约束向下：父给子一个 BoxConstraints(minW~maxW, minH~maxH)
  • 尺寸向上：子在约束范围内决定自己的 Size 返给父
  • 父定位置：父根据子的尺寸决定子的位置（Offset）
  • 理解布局问题先看约束传了什么：tight（强制）vs loose（自由）

三种 mark 方法的区别

  • markNeedsBuild() → 触发 Build Phase
  • markNeedsLayout() → 触发 Layout Phase（跳过 Build）
  • markNeedsPaint() → 只触发 Paint Phase（最轻量）
  • RepaintBoundary 隔离重绘：子树重绘不影响父
  • addPostFrameCallback → 当前帧结束后执行，可安全用 context

addPostFrameCallback — 帧后安全操作 context

Build Phase 执行期间不能修改 widget 树（会报 "setState during build" 错误）。 需要在 build 完成后立即执行某个操作时，用 addPostFrameCallback——它属于 SchedulerBinding 的 postFrameCallbacks，在 Composite 之后、下一帧 Build 之前执行。 

// 典型用途 1：initState 里需要用 context（此时 build 还未执行）
@override
void initState() {
  super.initState();
  WidgetsBinding.instance.addPostFrameCallback((_) {
    // 此时第一帧已经完成，context 可安全使用
    final size = context.size;
    Provider.of(context, listen: false).init(size);
  });
}

// 典型用途 2：确保 UI 构建完成后再显示悬浮窗/弹窗
@override
void initState() {
  super.initState();
  WidgetsBinding.instance.addPostFrameCallback((_) {
    if (!mounted) return;
    showDialog(context: context, builder: (_) => WelcomeDialog());
  });
}

// 注意：每次调用只执行一次（一次性）
// 需要每帧执行请用 addPersistentFrameCallback（持久回调）
性能陷阱：在 build() 里创建大对象、做网络请求、启动动画 → 每帧都执行，极度影响性能。 build() 应当是纯函数，毫秒级完成。

Dart 事件循环

Dart 主 Isolate（UI 线程） MicroTask Queue（优先级高） ← scheduleMicrotask() ← Future 的 .then() 内部回调 处理完才进入 Event Queue Event Queue（优先级低） ← Timer / Timer.periodic() ← I/O 完成回调 ← Future（new Future(...)） ← Stream 事件 ← Platform Channel 回调 await = 语法糖：Future.then(callback)；回调进 MicroTask Queue；I/O 等真实异步操作完成后经 Event Queue UI 帧渲染本身也是一个 Event

事件循环队列可视化

Future 完整入队时机

不同写法的 Future，回调入队的时机和目标队列不同。这是理解事件循环的基础。

写法回调何时入队进哪个队列
Future(() => ...)创建时立刻入队Event Queue
Future.microtask(() => ...)创建时立刻入队MicroTask Queue
Future.value(x).then(...)创建时立刻入队MicroTask Queue
Future.delayed(t, ...)t 时间后 OS 计时完成才入队Event Queue
http.get().then(...)网络响应回来后才入队Event Queue
File.readAsString().then(...)I/O 完成后才入队Event Queue

Future(() => ...) 是最基础的用法——把一段代码推迟到当前同步代码跑完之后执行，没有任何 I/O，没有等待，创建时立刻入队：

void main() {
  Future(() => print('B')); // 立刻把回调放入 Event Queue
  print('A');               // 同步代码先执行
}
// 输出：A → B
// 原因：print('A') 是同步代码先跑，Event Queue 里的回调等同步跑完才取出执行
// MicroTask 优先级高于 Event，全部清空才处理 Event
void main() {
  Future(() => print('Event'));             // → Event Queue
  Future.microtask(() => print('Micro'));   // → MicroTask Queue
  print('Sync');                            // 同步
}
// 输出：Sync → Micro → Event
两类 Future 的本质区别：
立刻入队的（Future() / Future.microtask()）：没有外部等待，只是把代码推迟执行，回调已经存在，直接排队。
完成后入队的（Future.delayed / I/O）：回调要等外部事件（计时器、OS I/O）触发后才放入队列，放入前回调"悬挂"在 .then() 里等待。

async / await 的本质：三层实现

官方文档原话："An async function runs synchronously until the first await keyword."（async 函数在遇到第一个 await 之前，是同步执行的。）

第一层：编译器语法糖

async/await 是编译器把代码切成回调片段的语法糖。遇到 await，后面的代码被打包成闭包注册到 .then()，当前函数立刻返回。

// 你写的
Future<void> fetchData() async {
  print('1');                              // await 前，同步执行
  await Future.delayed(Duration(seconds: 2));
  print('2');                              // 被打包成闭包
}

void main() {
  fetchData();   // 调用后：print('1') 执行，遇到 await 立刻返回
  print('3');    // main() 继续执行
}
// 输出：1 → 3 → （2秒后）2
// 编译器实际展开成
Future<void> fetchData() {
  print('1');                   // 同步，立刻执行
  return Future.delayed(Duration(seconds: 2))
    .then((_) {
      print('2');               // 被打包成闭包，注册到 .then()
    });                         // 函数在这里返回，不等待
}

第二层：回调的两个时机（容易混淆的关键点）

很多人认为"遇到 await 就把回调放入事件队列"——这是不准确的。

时机发生了什么
遇到 await 那一刻闭包注册到 .then()，操作开始（OS 开始计时/发包），当前函数返回。
闭包此时还没有进入事件队列。
操作完成那一刻OS 完成 I/O / 计时器到期 / 计算跑完，这时才把闭包放入 Event Queue 或 MicroTask Queue。
事件循环取到那一刻主线程执行这个闭包，await 后面的代码才真正运行。
如果"遇到 await 就立刻进队列"，那 Future.delayed(2s) 的回调会立刻被执行，2秒的延迟就失效了。正是因为完成时才入队，延迟才有意义。
官方文档原话（dart.dev/language/concurrency）：

"it also tells the event loop to hold the callback in the then() clause, until the HTTP request resolves"
→ 它同时告诉事件循环保留回调，直到请求完成。

"Dart code pauses, while non-Dart code (file I/O) executes in the Dart runtime or operating system. Once the operation returns a value, Dart code resumes."
→ Dart 代码暂停，非 Dart 代码（I/O）由操作系统独立执行。操作完成后，Dart 代码才继续。

为什么操作完成后不直接执行，而是放入队列？
因为操作系统完成 I/O 时，主线程不一定空闲——它可能正在执行别的代码。单线程没有"插队"机制，只能把回调放入队列排队，等主线程当前代码跑完，事件循环再取出执行。队列就是主线程"忙"与 OS "完成"之间的缓冲区。

第三层：谁来触发"把回调放入队列"

这取决于 await 后面的 Future 是怎么产生的：

Future 来源谁在干活主线程状态会卡 UI？
网络请求、文件 I/O、Timer操作系统独立完成，完成后通知 Dart 把回调入队完全空闲不卡
纯 Dart 计算（for 循环、JSON 解析）主线程亲自跑，跑完后把回调入队被占满卡
async/await 不创造任何并发，不把任何东西交给操作系统。交没交给 OS，取决于你调用的底层 API 是什么，和有没有写 async/await 无关。
// ✅ OS 干活，主线程空闲，不卡 UI
final response = await http.get(url);

// ❌ 主线程干活，卡 UI（加了 async/await 也没用）
Future<int> calculate() async {
  int sum = 0;
  for (int i = 0; i < 100000000; i++) sum += i; // 主线程跑
  return sum;
}
await calculate(); // 依然卡

// ✅ 正确做法：扔给 Isolate，主线程只等通知
final sum = await compute(heavyCalc, 100000000);
一句话总结：Dart 的异步本质是——用编译器把代码切成闭包片段，用事件循环决定何时执行每个片段，用 OS 完成真正的 I/O 工作。三层组合让单线程的 Dart 看起来像在"同时做多件事"。

Isolate — Dart 并发单元

  • 底层对应一个操作系统线程，但比线程多一个约束：独立内存堆，互相不共享任何数据
  • 不共享内存 → 不需要锁 → 不会有竞态条件
  • 通过 SendPort / ReceivePort 传递消息（值拷贝，不是引用）
  • UI 线程是主 Isolate，耗时操作（图片解码、JSON 解析）放子 Isolate
  • compute(func, message) → Flutter 封装，一次性子 Isolate
  • Isolate.spawn() → 长生命周期，双向通信
每个 Isolate 都有完整的事件循环（MicroTask Queue + Event Queue）。 区别只有一个：子 Isolate 没有 vsync，因为它不负责 UI。

Platform Channel

  • MethodChannel：Flutter ↔ Native 单次调用/响应
  • EventChannel：Native → Flutter 持续推送（Stream）
  • BasicMessageChannel：双向自定义消息
  • 序列化：StandardMessageCodec（int/double/String/List/Map）
  • 通信在 Platform Thread（Native）和 UI Thread（Dart）之间异步进行

Isolate vs 普通线程 / compute() 完整流程

普通多线程（Java/C++）

  • 多个线程共享同一块内存
  • 需要加锁防止竞态条件
  • 锁用错会死锁，用少会数据错乱

Dart Isolate

  • 每个 Isolate 有独立内存堆
  • 不共享内存 → 不需要锁
  • 通信只能靠消息传递（值拷贝）

compute(fn, data) 的完整执行流程：

主 Isolate compute(fn, data) 被调用 ↓ 创建子 Isolate（新的 OS 线程 + 独立内存堆） 把 data 拷贝一份发给子 Isolate（不是传引用） 主线程回到事件循环 → UI 正常刷新 子 Isolate（有自己的事件循环，但没有 vsync） 收到消息，执行 fn(data) 计算完成，把结果拷贝发回主 Isolate 子 Isolate 销毁 主 Isolate Event Queue 收到结果消息 await 恢复，继续执行后续代码
注意拷贝开销：两个 Isolate 之间传递的永远是数据的副本。传递一个 100MB 的列表，就要拷贝 100MB。大数据用 compute() 传递本身也有开销，适合计算密集型任务，不适合频繁传递大对象。

帧与帧之间：事件循环 × vsync 完整连接

Ch.6 讲了一帧之内发生什么，Ch.10 讲了事件循环的队列结构。这一节把两者连成一条完整的主线。

setState() 之后发生了什么

setState() 本身是同步的，调用完立刻返回，不会触发任何渲染。它只做了三件事：

1. 执行闭包
运行你传入的函数（如 _count++），修改状态数据
↓
2. markNeedsBuild()
把当前 Element 标记为 dirty，加入待重建队列
↓
3. scheduleFrame()
向系统预约下一个 vsync 信号，内部有去重检查：如果已经预约过则直接返回，因此同一帧内多次调用 setState() 只预约一次 vsync，Build Phase 只执行一次
结论：setState() 调用完之后，Build Phase 并没有立刻开始。程序继续执行后面的同步代码，事件循环继续处理其他事件，直到屏幕硬件发出下一个 vsync 信号，渲染才真正开始。

Flutter 的完整运行节奏是"事件循环"和"vsync"交替驱动：

vsync 信号到来 ↓ 帧渲染开始 Build Phase → 重建 dirty Element，执行 Widget diff Layout Phase → 约束向下，尺寸向上，确定每个节点的位置 Paint Phase → 生成绘制指令，构建 Layer 树 Composite → Engine 光栅化 Layer 树，输出画面到屏幕 ↓ 帧渲染结束 ↓ 【事件循环接管】 ① 清空 MicroTask Queue └─ await 恢复的回调、Future.then() 回调 ② 取一个 Event Queue 事件执行 └─ 用户点击 → onPressed → setState() → markNeedsBuild() + scheduleFrame() └─ 网络回调 → 更新数据 → setState() → scheduleFrame()（已预约则跳过） └─ Timer 触发 → 执行回调 ③ 再次清空 MicroTask Queue → 再取下一个 Event... ↓ vsync 信号到来（约 16ms 后） ↓ 下一帧渲染开始...
一句话总结：Flutter 的运行本质是两个节奏的叠加——事件循环负责驱动状态变化（处理用户输入、网络回调、定时器），vsync 负责驱动渲染（每 16ms 把累积的状态变化一次性反映到屏幕上）。两者通过 scheduleFrame() 衔接：状态变了就预约下一帧，vsync 到来时统一渲染。

卡顿的本质：主线程没有去读 Event Queue

UI 卡顿不是"计算量太大导致帧率下降"，而是主线程被同步代码占满，根本无法去读 Event Queue，导致 vsync 信号和 Timer 回调全部积压。

✅ async/await（不卡）

  • 遇到 await，把后续代码打包成回调登记好
  • 主线程立刻返回，继续读 Event Queue
  • vsync 照常到来，计数器照常跳
  • I/O 完成后回调进 Event Queue，主线程取出执行

❌ 同步大计算（卡）

  • 主线程进入 while / for 循环同步执行
  • 循环期间主线程无法读 Event Queue
  • vsync 信号进入 Event Queue 却无人取
  • Build / Layout / Paint 全部暂停，UI 冻结
操作类型主线程状态会卡 UI？解决方案
网络请求、文件 I/O、Timer等通知，空闲不卡async/await 即可
JSON 解析、图片处理、加密运算亲自计算，占满卡用 compute() 扔到子 Isolate
判断口诀：主线程是在"等通知"还是在"亲自算"？等通知用 async/await，亲自算用 compute()。async/await 解决不了计算量大的问题，它只是让主线程"优雅地等"，并不新建任何线程。

动画系统

SchedulerBinding + 三棵树的最佳实践体现
动画系统是"两大基石连接机制"的完美案例： AnimationController 通过 Ticker 每帧向 SchedulerBinding 注册 transientCallback， 值变化驱动 Widget rebuild，正是三棵树 + 事件循环协作的典型范式。

核心类层次

Animation<T> — 抽象基类，持有当前值 value 和状态 status
AnimationController — 驱动器，控制 forward/reverse/repeat，持有 Ticker CurvedAnimation — 包装器，把线性进度映射为曲线（Curves.easeIn 等） Tween<T>.animate() — 把 0.0~1.0 映射为任意类型的区间值
Ticker — 每帧回调，由 TickerProvider（SingleTickerProviderStateMixin）提供

AnimationController 与 SchedulerBinding 的连接

AnimationController.forward() ↓ Ticker.start() ↓ SchedulerBinding.scheduleFrameCallback() ← 注册 transientCallback ↓ vsync 到来（≈16ms） ↓ Ticker._tick(Duration elapsed) — 收到帧时间戳 ↓ 计算 value = elapsed / duration（0.0 → 1.0） ↓ notifyListeners() — 通知所有监听者 ↓ AnimatedWidget.setState() / AnimatedBuilder rebuild ↓ 重复注册下一帧 transientCallback，直到 value == 1.0 ↓ 动画结束，Ticker 停止
必须 dispose：AnimationController 持有 Ticker，Ticker 持有对 SchedulerBinding 的引用。 不 dispose 会导致控制器在 widget 销毁后仍每帧回调，内存泄漏且可能 setState after dispose。

完整动画代码示例

// ① 最底层：手动控制动画
class _FadeState extends State
    with SingleTickerProviderStateMixin {   // 提供 Ticker vsync
  late AnimationController _ctrl;
  late Animation _opacity;

  @override
  void initState() {
    super.initState();
    _ctrl = AnimationController(
      vsync: this,                         // this 就是 TickerProvider
      duration: const Duration(milliseconds: 500),
    );
    _opacity = CurvedAnimation(
      parent: _ctrl,
      curve: Curves.easeInOut,             // 线性 → 曲线
    );
    _ctrl.forward();                       // 触发动画
  }

  @override
  Widget build(BuildContext context) {
    return FadeTransition(                 // AnimatedWidget 子类，自动监听 _opacity
      opacity: _opacity,
      child: widget.child,
    );
  }

  @override
  void dispose() {
    _ctrl.dispose();                       // 必须 dispose！
    super.dispose();
  }
}

// ② AnimatedBuilder：任意 Widget 用动画值
AnimatedBuilder(
  animation: _ctrl,
  builder: (context, child) {
    return Transform.scale(
      scale: _ctrl.value,                  // 每帧用最新值
      child: child,                        // child 不变时不重建
    );
  },
  child: const Icon(Icons.star),           // 静态部分缓存，不参与每帧 rebuild
)

// ③ Tween：值类型映射
final _colorAnim = ColorTween(
  begin: Colors.blue,
  end: Colors.red,
).animate(_ctrl);
// _colorAnim.value 在 forward() 时从 blue 渐变到 red

隐式动画（推荐优先使用）

Layer 树与 Composite 阶段

渲染管线最后一公里

Paint Phase 产生了什么？

Ch.6 讲过渲染管线分四步：Build → Layout → Paint → Composite。前三步都在 Dart/Framework 层，Composite 是唯一跨入 C++ Engine 的阶段。

Paint Phase 并不直接把像素写到屏幕——它生成一棵 Layer 树，Layer 树再交给 Engine 合成上屏。理解这棵树是理解 RepaintBoundary 性能优化、透明度/裁剪/变换的底层前提。

RenderObject.paint() ↓ PaintingContext — 收集绘制指令 ↓ 写入 PictureRecorder → Picture（DisplayList，GPU 可执行的绘制命令序列） ↓ 封装进 PictureLayer（Layer 树叶子节点） ↓ 汇聚成 Layer 树（ContainerLayer 根 → 子 Layer 树） ↓ Flutter Engine (C++) → Skia / Impeller → GPU → 屏幕

Layer 类型速查

Layer 类型职责对应 Widget/RenderObject
PictureLayer持有一个 Picture，是 Layer 树的叶子节点，真正存储绘制指令普通 RenderObject.paint() 的输出
OffsetLayer平移子层，不产生像素，只做坐标偏移根 Layer、ContainerLayer 默认
TransformLayer对子层做矩阵变换（旋转/缩放/透视）Transform widget
OpacityLayer对子层整体应用透明度Opacity widget（透明度 < 1 时）
ClipRectLayer矩形裁剪子层ClipRect widget
ClipRRectLayer圆角矩形裁剪ClipRRect widget
ClipPathLayer任意路径裁剪ClipPath widget
BackdropFilterLayer对下层内容做模糊/滤镜BackdropFilter widget
PhysicalModelLayer阴影 + 裁剪（Material 阴影的来源）Material / Card
关键结论：透明度、变换、裁剪等效果都不是在 Paint 阶段像素级处理的，而是生成对应的 Layer 节点，交给 GPU 在 Composite 时以硬件加速合成。这是 Flutter 性能高的根本原因之一。

RepaintBoundary 的真正底层原理

Ch.6 提到 RepaintBoundary 可以隔离重绘区域，但为什么？答案在 Layer 树里。

普通 RenderObject 共用父节点的 PictureLayer 父节点脏了 → 整块 PictureLayer 重新录制 → 所有子节点都重绘 加了 RepaintBoundary 的 RenderObject 拥有自己独立的 OffsetLayer（新建 PaintingContext） 父节点脏了 → 父的 PictureLayer 重录 → 子的 OffsetLayer 直接复用缓存 子节点脏了 → 只重录子自己的 PictureLayer → 父的 PictureLayer 不受影响

实质：RepaintBoundary 让子树拥有独立的 Layer（实际是 OffsetLayer），Engine 在 Composite 时可以直接复用上一帧该 Layer 的 GPU 纹理缓存，不必重新光栅化。

不加 RepaintBoundary

  • 父子共享 PictureLayer
  • 父重绘 → 子一起重绘
  • 适合静态组合 UI

加 RepaintBoundary

  • 子拥有独立 OffsetLayer
  • 父重绘 → 子复用 GPU 缓存
  • 适合高频动画、滚动列表中的复杂卡片
不要滥用：每个 RepaintBoundary 都占用独立 GPU 纹理内存。静态 UI 加了反而浪费内存、增加合成开销。只在频繁重绘的子树边界使用。

Composite 阶段：Engine 做了什么

Flutter Framework 把 Layer 树根节点传给 Scene ↓ window.render(scene) Flutter Engine (C++) ① 遍历 Layer 树，决定每个 Layer 是否需要重新光栅化（rasterize） ② 已缓存的 Layer → 直接复用 GPU 纹理 ③ 需要重绘的 Layer → 调用 Skia / Impeller 光栅化 Picture → 生成 GPU 纹理 ④ 把所有 GPU 纹理按 Layer 树结构合成（composite） ↓ GPU 输出最终帧 → 屏幕
渲染器原理优势
SkiaJIT 编译 GLSL Shader，首帧可能卡顿（shader compilation jank）成熟稳定，兼容性好
ImpellerAOT 预编译所有 Shader（打包时编译），彻底消除 shader jank首帧流畅，iOS 默认，Android 逐步启用

完整渲染管线（补全版）

Flutter 每渲染一帧，都会按顺序经过以下四个阶段。每个阶段各司其职，前一个阶段的输出是下一个阶段的输入。

① Build Phase
框架收集所有被标记为"脏"的 Element，依次调用 State.build() 拿到新的 Widget 子树。然后对比新旧 Widget（diff），决定哪些 Element 可以复用、哪些需要销毁重建。
产出：Element 树更新完毕，每个 Element 知道自己对应哪个 Widget。
↓
② Layout Phase
从根节点出发，父节点把 BoxConstraints（允许的最小/最大宽高范围）向下传给每一个子节点。子节点在收到约束后，调用 performLayout()，在约束范围内决定自己的 size，再把 size 返回给父节点。父节点根据子节点的 size 决定子节点摆放的位置（Offset）。
产出：每个 RenderObject 都有了确定的尺寸和在屏幕上的位置。
↓
③ Paint Phase
从根节点出发，依次调用每个 RenderObject 的 paint()。paint() 内部通过 Canvas 发出绘制指令（画矩形、画文字、画路径等），这些指令不会立刻变成像素，而是被 PictureRecorder 录制成一个 Picture（可理解为"绘制脚本"）。多个 RenderObject 的 Picture 被组织进 Layer 树——普通节点共用同一个 PictureLayer，加了 RepaintBoundary 的子树拥有独立的 Layer，可以在下一帧直接复用上帧的缓存，不必重新录制。
产出：一棵 Layer 树，每个叶子节点持有一份 Picture（绘制脚本）。
↓
④ Composite
Flutter Framework 把 Layer 树交给 C++ Engine。Engine 遍历 Layer 树，对每个 Layer 判断：如果上帧已经光栅化过且内容未变，直接复用 GPU 纹理缓存；如果内容有变化，则调用 Skia 或 Impeller 把 Picture"光栅化"成 GPU 纹理（真正变成像素）。最后把所有 GPU 纹理按 Layer 树的层叠顺序合成，输出最终画面到屏幕。
产出：屏幕上显示的那一帧画面。

并不是每次更新都要完整走完四个阶段。Flutter 提供三种"标记"方法，精确控制从哪个阶段开始执行，避免不必要的计算：

触发方式从哪个阶段开始典型场景
setState() → markNeedsBuild()① Build → ② → ③ → ④State 数据变化，Widget 树需要重建
markNeedsLayout()② Layout → ③ → ④（跳过 Build）尺寸相关属性变化，但不需要重建 Widget
markNeedsPaint()③ Paint → ④（跳过 Build + Layout）只有视觉属性变化（颜色、进度），尺寸不变
RepaintBoundary 子树④ Composite（③ 直接复用缓存）子树内容未变，父节点重绘时子树完全不动
选用原则：能用 markNeedsPaint() 就不用 markNeedsLayout()，能用 RepaintBoundary 隔离就不让子树参与每帧重绘。触发的阶段越靠后，开销越小。

BoxConstraints：布局的核心约束模型

BoxConstraints(minWidth, maxWidth, minHeight, maxHeight) 是父传给子的"框"，子必须在这个框内决定自己的 Size。

约束类型条件含义典型来源
Tight（紧）minW == maxW && minH == maxH子的尺寸被完全固定，没有选择权SizedBox、ConstrainedBox、屏幕根节点
Loose（松）minW == 0 && minH == 0子可以在 0 到 max 范围内自由选择Column/Row 的主轴方向、Center
Bounded（有界）max < infinity子有明确的上限大多数正常布局
Unbounded（无界）max == infinity子可以要多大就多大ListView 主轴方向、Column 主轴
经典 Bug：在 Column 里放 ListView 会报 "Vertical viewport was given unbounded height"——Column 给子传 unbounded 高度约束，ListView 不知道自己该多高。解决：给 ListView 加 Expanded 或固定高度。
// performLayout 里读取约束、设置尺寸的标准写法
@override
void performLayout() {
  // constraints 是父传下来的 BoxConstraints
  final double width = constraints.maxWidth;   // 撑满父宽
  final double height = constraints.constrainHeight(48.0); // 尝试48，约束内取值
  size = Size(width, height); // 必须在 performLayout 里设置 size！
}

// ── Step 4: RenderObject 层（真正测量 + 绘制）──
class RenderRainbowProgress extends RenderBox {
  double _progress;
  double _barHeight;

  RenderRainbowProgress({
    required double progress,
    required double barHeight,
  })  : _progress = progress,
        _barHeight = barHeight;

  // Setter：外部更新属性时触发重绘（不需要重新 layout）
  set progress(double value) {
    if (_progress == value) return;
    _progress = value;
    markNeedsPaint(); // 只触发 Paint Phase，最轻量
  }

  set barHeight(double value) {
    if (_barHeight == value) return;
    _barHeight = value;
    markNeedsLayout(); // 高度变了，需要重新 layout
  }

  // ── 告诉父节点这个 Widget 是否有固定尺寸偏好 ──
  @override
  double computeMinIntrinsicHeight(double width) => _barHeight;

  @override
  double computeMaxIntrinsicHeight(double width) => _barHeight;

  // ── Layout：测量并设置自己的 size ──
  @override
  void performLayout() {
    // 撑满父宽，高度固定为 _barHeight（在约束范围内取值）
    size = Size(
      constraints.maxWidth,
      constraints.constrainHeight(_barHeight),
    );
  }

  // ── Paint：用 Canvas 绘制彩虹进度条 ──
  @override
  void paint(PaintingContext context, Offset offset) {
    final canvas = context.canvas;
    final double w = size.width;
    final double h = size.height;
    final radius = Radius.circular(h / 2);

    // 1. 背景轨道（灰色圆角矩形）
    final trackPaint = Paint()
      ..color = const Color(0xFFE0E0E0)
      ..style = PaintingStyle.fill;
    canvas.drawRRect(
      RRect.fromRectAndRadius(offset & size, radius),
      trackPaint,
    );

    // 2. 进度条（彩虹渐变，宽度 = 总宽 * progress）
    final double progressWidth = w * _progress.clamp(0.0, 1.0);
    if (progressWidth > 0) {
      final progressRect = Rect.fromLTWH(
          offset.dx, offset.dy, progressWidth, h);
      final progressPaint = Paint()
        ..shader = const LinearGradient(
          colors: [
            Color(0xFFFF6B6B), // 红
            Color(0xFFFFD93D), // 黄
            Color(0xFF6BCB77), // 绿
            Color(0xFF4ECDC4), // 青
            Color(0xFF45B7D1), // 蓝
            Color(0xFF9B59B6), // 紫
          ],
        ).createShader(Rect.fromLTWH(offset.dx, offset.dy, w, h))
        ..style = PaintingStyle.fill;
      canvas.drawRRect(
        RRect.fromRectAndRadius(progressRect, radius),
        progressPaint,
      );
    }
  }
}

关键机制：updateRenderObject vs createRenderObject

方法何时调用职责
createRenderObject()Widget 首次 mount，Element.createRenderObject() 触发，只调用一次new 一个 RenderObject，设置初始属性
updateRenderObject()父组件 setState() 导致 Widget rebuild，但类型未变（canUpdate = true），多次调用把新 Widget 的配置同步到已有 RenderObject，让 RenderObject 决定是否 markNeedsPaint / markNeedsLayout
设计哲学：Widget 是轻量配置对象，随 setState 频繁 new；RenderObject 是重量级对象，最大化复用。updateRenderObject 就是两者之间的同步桥梁，只更新变化的属性，最小化重绘范围。

mark 三兄弟的精确语义

方法触发阶段何时用
markNeedsBuild()Build + Layout + PaintState 变化需要 Widget 重建（由 setState 调用）
markNeedsLayout()Layout + Paint尺寸/约束相关属性变了（barHeight 变化）
markNeedsPaint()Paint only只有视觉属性变了，尺寸不变（progress 变化、颜色变化）
性能原则：setter 里能用 markNeedsPaint() 就不用 markNeedsLayout()——少触发一个 Layout Phase，节省计算。只有影响到自身 size 或子节点位置的属性才需要 markNeedsLayout()。

有子节点的 RenderBox（SingleChildRenderObjectWidget）

有子节点时继承 SingleChildRenderObjectWidget，RenderObject 继承 RenderProxyBox 或 RenderBox with RenderObjectWithChildMixin，需要手动布局子节点：

@override
void performLayout() {
  if (child != null) {
    // 把约束传给子节点（可以修改约束，实现 Padding / SizedBox 效果）
    child!.layout(constraints, parentUsesSize: true);
    size = child!.size; // 跟随子节点大小
  } else {
    size = constraints.smallest;
  }
}

@override
void paint(PaintingContext context, Offset offset) {
  if (child != null) {
    // 先画背景，再画子节点
    context.canvas.drawRect(offset & size, _backgroundPaint);
    context.paintChild(child!, offset); // 让子节点自己画
  }
}
注意：调用 child.layout() 时，parentUsesSize: true 表示父节点依赖子的 size。设置为 false 时 Flutter 可以做更多优化（子重新 layout 不强制触发父重绘）。

// ❌ 整个页面是一个 StatefulWidget，任何状态变化重建整页
class BadPage extends StatefulWidget { ... }

// ✅ 只把频繁变化的部分抽成独立 StatefulWidget
class CounterWidget extends StatefulWidget { ... } // 只重建这一小块
class StaticContent extends StatelessWidget { ... } // 永远不重建

③ 不要重写 Widget 的 operator==

原理：canUpdate() 只判断 runtimeType 和 key，不用 ==。重写 operator== 意味着必须同时重写 hashCode，引入额外计算开销，而且对 diff 没有任何收益。

官方明确建议：不要在 Widget 对象上重写 operator ==。Widget 是值对象，频繁 new，重写 == 只增加开销。

从渲染管线 / Layer 树推导的优化

④ RepaintBoundary — 隔离高频重绘区域

原理：子树拥有独立 Layer，Engine 在 Composite 阶段直接复用上帧 GPU 纹理，不重新光栅化。

适合加的场景

  • 复杂动画组件边界
  • 实时更新的图表、计时器
  • 滚动列表中的复杂卡片

不要滥用

  • 每个 RepaintBoundary 占一份 GPU 纹理内存
  • 静态 UI 加了反而增加合成开销
  • 只在频繁重绘的子树边界使用

⑤ 避免使用 Opacity widget，改用半透明颜色或 AnimatedOpacity

原理：Opacity widget 底层创建 OpacityLayer，强制子树离屏渲染再合成，即使子树内容没有变化也有额外 GPU 开销。

// ❌ 创建 OpacityLayer，子树离屏渲染，有额外开销
Opacity(opacity: 0.5, child: MyWidget())

// ✅ 静态场景：直接用半透明颜色，不产生额外 Layer
Container(color: Colors.red.withOpacity(0.5))

// ✅ 动画场景：AnimatedOpacity 内部有优化，避免每帧全量重绘
AnimatedOpacity(
  opacity: _opacity,
  duration: const Duration(milliseconds: 300),
  child: MyWidget(),
)

⑥ mark 方法精确匹配

原理：三种 mark 方法触发的渲染阶段不同，触发阶段越靠后开销越小。

方法触发阶段使用时机
markNeedsBuild()Build + Layout + Paint + CompositeState 数据变化，Widget 树需要重建（setState 调用）
markNeedsLayout()Layout + Paint + Composite尺寸相关属性变化（自定义 RenderObject）
markNeedsPaint()Paint + Composite（最轻量）只有视觉属性变化，尺寸不变（颜色、进度条进度）

从动画系统推导的优化

⑦ AnimatedBuilder 的 child 缓存

原理：AnimatedBuilder 每帧都调用 builder。静态子树放在 builder 里每帧重建；放在 child 参数里，框架只创建一次并缓存，builder 收到的是同一个对象引用。

// ❌ Text 每帧都重建，浪费
AnimatedBuilder(
  animation: _ctrl,
  builder: (context, _) => Row(children: [
    Transform.scale(scale: _ctrl.value, child: const Icon(Icons.star)),
    const Text('标题'), // 静态内容放在 builder 里，每帧重建
  ]),
)

// ✅ 静态部分放 child，框架缓存，builder 每帧复用同一实例
AnimatedBuilder(
  animation: _ctrl,
  child: const Text('标题'),         // 只创建一次
  builder: (context, child) => Row(children: [
    Transform.scale(scale: _ctrl.value, child: const Icon(Icons.star)),
    child!,                          // 复用缓存，不重建
  ]),
)

从事件循环推导的优化

⑧ 耗时操作用 compute() 扔到 Isolate

原理：主线程同步大计算会占满 Event Queue，vsync 信号进不来，UI 冻结。compute() 把计算扔到子 Isolate，主线程只等通知，不阻塞。

// ❌ 主线程解析大 JSON，UI 冻结
final data = jsonDecode(hugJsonString);

// ✅ 扔给子 Isolate，主线程空闲
final data = await compute(jsonDecode, hugeJsonString);

⑨ build() 必须是纯函数

原理：Build Phase 每帧都可能执行，build() 里的代码每帧都跑。耗时操作放在 build() 里直接影响帧率。

// ❌ 每帧都创建 StreamController，每帧都发起网络请求
Widget build(BuildContext context) {
  final controller = StreamController(); // 每帧 new
  http.get(url);                         // 每帧请求
  return Text('...');
}

// ✅ 一次性初始化放在 initState
@override
void initState() {
  super.initState();
  _controller = StreamController(); // 只创建一次
  _loadData();                      // 只请求一次
}

BLoC / Stream 层面的优化

⑩ buildWhen 过滤不必要的重建

// 只有 count 变化时才重建，其他字段变化不触发
BlocBuilder<MyBloc, MyState>(
  buildWhen: (prev, curr) => prev.count != curr.count,
  builder: (context, state) => Text('${state.count}'),
)

⑪ context.select 精准订阅单个字段

// 只有 count 变化时，这个 Widget 才重建
// 利用 InheritedElement 的切面依赖，O(1) 精准触发
final count = context.select((MyBloc b) => b.state.count);
