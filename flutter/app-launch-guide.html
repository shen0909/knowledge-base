Android Studio & Android SDK

Android 官方 IDE，内置模拟器、Logcat 调试、Gradle 构建等一切工具
📖 安装文档 📦 SDK Manager
Android Studio 是基于 IntelliJ IDEA 的官方 IDE。安装时会附带 Android SDK（系统 API 库）、Android Emulator（模拟器）、ADB（调试桥）等工具。日常开发主要用它编写代码、查看 Logcat 日志、运行模拟器。

SDK Manager（Tools → SDK Manager）用来管理已安装的 Android API 版本和构建工具（Build Tools）。AVD Manager（Tools → Device Manager）用来创建和管理模拟器。
💡 Flutter 开发也可以用 VS Code，但原生 Android 调试（查看布局、查 JNI 报错）在 Android Studio 里更方便。
  • Android SDK Platform：对应 API Level，如 API 35 = Android 15
  • Build Tools：Gradle 调用的编译工具，通常装最新版即可
  • NDK：Native Development Kit，调用 C/C++ 代码时需要
  • ADB：命令行工具，可安装 APK、查看日志、截图
  • Logcat：实时查看 App 运行日志，调试 crash 的主要手段
  • 模拟器比真机慢，建议同时准备一台 Android 真机

JDK — Java 运行环境

Gradle 构建系统用 Java 写的，必须有 JDK 才能运行
📖 Android JDK 文档 ☕ Temurin JDK
Gradle 本身是 Java 程序，必须有 JDK 才能运行。Android Studio 内置了一个 JetBrains Runtime（JBR），但它并不总是与所有 Gradle/Android Gradle Plugin 版本兼容。

推荐单独安装 Eclipse Temurin JDK 17（OpenJDK 的社区发行版），并在 ~/.gradle/gradle.properties 中指定：
org.gradle.java.home=/Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home
💡 常见坑：Android Studio 的 JBR 在某些系统下与 android-34 的 transforms 不兼容，会报 jlink 错误。换成 Temurin JDK 17 可解决。
📌 本项目踩坑
构建时报错 JdkImageTransform: core-for-system-modules.jar jlink process failure，原因是 Android Studio 内置 JBR 与当前 Gradle 版本不兼容。
解决方法：在 ~/.gradle/gradle.properties 中添加 org.gradle.java.home=/Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home，全局切换到 Temurin JDK 17。

Xcode & iOS 工具链（macOS only）

开发 iOS App 的强制要求；在 Mac 上同时搭好可兼顾双端
📖 Xcode 文档 🍎 Flutter iOS 环境
iOS App 只能在 macOS 上编译，必须安装 Xcode（App Store 免费下载）。Xcode 内置 iOS 模拟器、Swift/Objective-C 编译器、Instruments 性能分析工具。

安装后还需要运行 sudo xcode-select --switch /Applications/Xcode.app 和 sudo xcodebuild -runFirstLaunch 完成命令行工具初始化；Flutter 还要求安装 CocoaPods（iOS 依赖管理器）。
💡 Windows / Linux 无法编译 iOS 包，这是 Apple 的硬限制。团队内通常需要至少一台 Mac 负责 iOS 构建。
  • Simulator：Xcode 内置 iOS 模拟器，无需真机可快速测试
  • CocoaPods：iOS 原生依赖管理，类似 Android 的 Gradle 依赖
  • 命令行工具：xcode-select --install 安装基础工具
  • flutter doctor 会检查 Xcode 安装状态并给出修复建议
  • 真机调试需要 Apple ID，上架需要付费开发者账号（$99/年）
  • flutter build ipa 生成 iOS 安装包

Flutter — 跨平台 UI 框架

一套代码同时运行在 Android、iOS、Web、桌面

网络层 — dio / Retrofit / HTTP 通信

App 与服务器交换数据的通道；如何发请求、处理错误、统一管理 Token
📖 dio 文档 🔧 retrofit 🌐 Flutter 网络
App 与服务器通信的基础是 HTTP 请求。Flutter 生态中最主流的 HTTP 库是 dio，它比内置的 http 包功能更完整，支持拦截器、文件上传、超时、取消请求等。

dio：直接发起 GET/POST 等请求，手动处理响应和错误。灵活但重复代码多。

Retrofit（retrofit + build_runner）：在 dio 之上的声明式封装。用注解描述 API 接口（类似 Java 的 Retrofit），自动生成请求代码，接口定义清晰，适合接口数量多的项目。

Interceptor（拦截器）：dio 的核心机制，可以在请求发出前/响应返回后统一处理逻辑，如自动加 Token 到 Header、统一处理 401 重新登录、记录请求日志。
💡 一个成熟的网络层通常包括：dio 实例 + 若干 Interceptor（Token注入、错误处理、日志）+ Retrofit 定义的接口层，这样每个业务只需调用接口方法，不关心底层细节。
🔁 一次 API 请求的完整生命周期
① 业务代码调用 Retrofit 接口方法
② 请求拦截器：自动注入 Authorization Token、添加公共参数
③ dio 发出 HTTP 请求到服务器
④ 服务器返回响应
⑤ 响应拦截器：统一解析业务错误码（如 401 → 跳登录页，网络超时 → 弹提示）
⑥ Retrofit 将 JSON 反序列化为 Dart 对象
⑦ 业务代码拿到结果，更新 UI
  • BaseOptions：统一配置 baseUrl、超时时长、公共 Header
  • Interceptor：onRequest / onResponse / onError 三个钩子
  • CancelToken：页面销毁时取消未完成请求，防止内存泄漏
  • HTTP/2：dio 可搭配 dio_http2_adapter 启用 HTTP/2，减少连接建立开销
  • Retrofit 接口用 @GET / @POST 注解，build_runner 自动生成实现类
  • 调试网络请求：talker_dio_logger 插件可在控制台美化打印请求/响应
📌 本项目示例
本项目同时使用 dio: ^5.8.0 和 retrofit: ^4.5.0。Retrofit 定义各业务接口（登录、充值、联系人同步等），build_runner 生成 .g.dart 文件。

talker_dio_logger: ^5.0.2 作为 dio 的 Interceptor 接入，开发阶段在控制台以彩色格式打印每个请求的 URL、Header、Body 和响应，方便调试接口问题。

dio_http2_adapter: ^2.6.0 用于对特定服务器启用 HTTP/2 连接，减少 VoIP 相关 API 的延迟。

状态管理 — Provider / GetX / BLoC

解决「数据变了，UI 怎么知道要刷新」的问题；Flutter 生态有多种方案
📖 状态管理对比 🟣 Provider ⚡ GetX 🧱 BLoC
Flutter 的 UI 是「数据驱动」的：数据变了，调用 setState() 触发 Widget 重建，UI 自动更新。但 setState() 只在当前 Widget 内生效，当多个页面需要共享同一份数据时（如用户登录状态、余额、通话状态），就需要状态管理方案来跨 Widget 传递和同步数据。

三种主流方案的定位：
Provider：官方推荐，轻量、与 Flutter 理念契合，适合中小型项目。
GetX：一体化框架，集状态管理、路由、依赖注入于一身，写法最简洁，本项目大量使用。
BLoC：严格的单向数据流（事件→状态），测试友好，适合业务复杂的大型项目。
💡 没有「最好」的方案，只有适合项目规模和团队习惯的方案。新手从 Provider 入门最平滑；想快速开发选 GetX；对代码可测试性要求高选 BLoC。
📊 三种方案对比
Provider GetX BLoC
学习曲线 低 低 高
代码量 中 少 多
可测试性 好 一般 极好
额外功能 仅状态管理 路由+依赖注入 仅状态管理
  • Provider：ChangeNotifier + notifyListeners() + Consumer<T> 三件套
  • GetX：Obx(() => Text(controller.name))，响应式变量加 .obs 后缀即可
  • BLoC：Event → Bloc → State，UI 只能发 Event，不能直接改数据
  • 同一个项目混用多种方案是正常的，不同场景选最合适的
  • 全局状态（登录用户信息）用状态管理；局部 UI 状态（按钮是否 loading）用 setState() 即可
  • GetX 的 Get.to() 路由和 Get.find() 依赖注入是额外加分项
📌 本项目示例
本项目混用了三种方案，各有侧重：

Provider（provider: ^6.1.5）：管理用户账号信息、通话状态等需要跨多个页面共享的全局数据。

GetX（get: 4.6.6）：用于页面路由跳转（Get.to() / Get.back()）、Controller 的依赖注入，以及部分页面内的轻量状态管理。

BLoC（flutter_bloc: ^8.1.5）：用于业务逻辑较复杂的模块（如充值流程、广告加载状态机），事件驱动保证状态流转清晰可追踪。

ScopedModel（scoped_model: ^2.0.0）：部分历史代码遗留，功能类似 Provider，团队逐步迁移中。

Platform Channel — Flutter 与原生代码通信

Flutter 调用相机、蓝牙、厂商 SDK 等原生能力的底层桥接机制
📖 Platform Channel 文档 🔧 开发 Flutter 插件
Flutter 使用 Dart 语言，但手机的硬件能力（相机、蓝牙、传感器）和厂商提供的 SDK（如本项目的 JC 通话 SDK、TradPlus 广告 SDK）是用 Java/Kotlin（Android）或 OC/Swift（iOS）写的。

Flutter 通过 Platform Channel 机制实现跨语言调用：Dart 层发送消息到一个「命名通道」，原生层监听这个通道并处理，结果异步返回给 Dart。

日常使用中，开发者通常不需要自己写 Platform Channel——社区和厂商已经将常用功能封装成 Flutter 插件（Plugin），直接在 pubspec.yaml 中添加依赖即可使用。但当厂商只提供原生 SDK（没有 Flutter 插件）时，就需要自己封装。
💡 理解 Platform Channel 有助于解释：为什么 Flutter 插件同时有 lib/（Dart 代码）、android/（Java/Kotlin 代码）、ios/（OC/Swift 代码）三个目录——Dart 层是接口，原生层是实现。
🏗️ Flutter 插件的目录结构
flutter_plugin/
  ├── lib/            ← Dart 接口层（调用者看到的 API）
  ├── android/        ← Android 原生实现（Java/Kotlin）
  ├── ios/            ← iOS 原生实现（OC/Swift）
  └── pubspec.yaml    ← 声明这是一个 plugin
  • MethodChannel：最常用，Dart 调用原生方法，等待一次性返回值
  • EventChannel：原生持续向 Dart 推送事件流（如传感器数据、来电通知）
  • BasicMessageChannel：双向持续通信，用于复杂的消息交换场景
  • Pigeon：Google 出品的代码生成工具，自动生成类型安全的 Channel 代码，消除手写通道时的类型错误
  • pub.dev 上有数千个现成插件，优先找现成的，再考虑自己封装
  • 插件问题 debug：原生层的报错只在 Logcat（Android）/ Xcode Console（iOS）可见
📌 本项目示例
本项目大量使用封装了 Platform Channel 的私有插件，全部托管在公司 GitLab：

jcmanager：封装了 JusTalk 的原生通话 SDK（JCClient），Dart 层调用 jcmanager.call(number)，底层通过 MethodChannel 调用 Android/iOS 各自的通话 SDK 实现发起通话。

flutter_dtmf：封装原生的 DTMF 拨号音发送，按键时通过 MethodChannel 通知原生层发出音频。

advertising_info：通过 MethodChannel 获取设备的 Advertising ID（IDFA/GAID），原生层读取系统级 API，Dart 层只拿到一个字符串结果。

flutter_local_notifications：用 EventChannel 监听来电推送，原生层收到推送后持续向 Dart 层推送来电事件，触发 Flutter UI 展示来电界面。

Product Flavors — 多渠道 / 多品牌构建

用一套代码同时构建出多个不同品牌的 App（即「马甲包」）
📖 Build Variants 文档
Product Flavors 是 Android Gradle 的功能。在 build.gradle 中声明多个 flavor，每个 flavor 可以有独立的包名、App 名称、图标、资源文件。构建时选择不同 flavor 就会生成对应品牌的 App。
💡 为什么需要：一个团队同时运营多个品牌的同类 App（如 Ding Call、Call 360），共享同一套业务逻辑，只有品牌 UI 和配置不同。通过 Flavor 可以高效复用代码，避免维护多个独立仓库。
📌 本项目示例
本项目在 android/app/build.gradle 的 productFlavors 中定义了 12 个马甲：juscall、duovoice、dingcall、call360 等。打包时用 --flavor call360 指定要构建哪个马甲。每个马甲在 android/app/src/马甲名/ 下存放各自的图标和配置。

App 签名（Keystore）— Android 身份证

证明这个 App 是由你发布的，防止他人篡改
📖 签名文档 🔑 keytool 工具
Android 规定每个 App 发布前必须用「私钥」签名。这个私钥存储在 keystore 文件（.jks / .keystore）里。签名后的 App 会附带公钥指纹（SHA-1 / SHA-256），系统和第三方服务用它来验证来源。

keystore 一旦丢失，该 App 就永远无法更新（Play 会拒绝不同签名的升级包），因此必须妥善保管。
💡 关键规则：signingConfigs 中的 storeFile 指向哪个 keystore 文件，必须通过 key.properties 确认，不能靠名字猜测。
  • debug keystore：本地开发调试用，系统自动生成
  • release keystore：正式发布用，需自己生成并保管
  • SHA-1：证书指纹，需注册到 Firebase、Google 登录等服务
  • Play App Signing：将签名密钥托管给 Google，更安全
  • 查看签名：keytool -printcert -jarfile app.aab
  • 本项目有两个 keystore：justalk.keystore 和 juscall.keystore
📌 本项目示例
key.properties 中：storeFile=../justalk.keystore（对应 release）、jcStoreFile=../juscall.keystore（对应 jcRelease）。为 call360 配签名时，先查 google-services.json 里的 SHA1，与两个 keystore 的 SHA1 比对，才能确定用哪个 signingConfig。

Source Sets — Flavor 如何找到自己的资源文件

Gradle 按固定目录规则自动合并资源，flavor 目录的同名文件会覆盖 main 目录
📖 Source Sets 文档
Android 规定了固定的目录查找规则：android/app/src/ 下有两类目录——main（所有 flavor 共享的基础资源）和 flavor 名（该 flavor 专属资源）。

构建某个 flavor 时，Gradle 先加载 src/main/ 的全部资源，再加载 src/flavor名/ 的资源，同名文件直接覆盖，不同名文件正常合并。因此每个马甲只需要放「与 main 不同的文件」，无需重复放所有资源。
💡 优先级：src/flavor名/ > src/main/。这个规则由 Gradle 自动处理，不需要写任何代码。
  • 图标（mipmap）：放 flavor 目录 → 覆盖 main 的默认图标
  • google-services.json：放 flavor 目录根部 → 自动关联对应 Firebase 项目
  • strings.xml / colors.xml：放 flavor 目录 → 覆盖 main 的默认值
  • layout、其他未覆盖资源：继续使用 main 目录的文件
  • flavor 目录只需放「差异文件」，大幅减少重复
  • 多个 flavor 各自独立，互不影响
📌 本项目示例（call360）
src/main/res/drawable-hdpi/ic_logo_288.png（默认图标）被
src/call360/res/drawable-hdpi/ic_logo_288.png（call360 专属图标）自动覆盖。
google-services.json 放在 src/call360/ 根目录，构建 call360 时自动连接 call360 的 Firebase 项目；构建 dingcall 时则使用 src/dingcall/google-services.json，完全隔离。

版本号管理策略 — versionCode & versionName

两个版本号含义完全不同：一个给机器判断新旧，一个给用户看
📖 Android 版本文档 🎯 Flutter 版本配置
Android 每个 App 有两个独立的版本号：

versionCode（整数）：给 Google Play 和系统看的，判断「哪个包更新」。每次发布必须严格递增，否则 Play 会拒绝上传。用户看不到这个数字。

versionName（字符串）：给用户看的显示版本号，如 1.2.3。格式自由，Play 不限制，可以不递增——但不递增会让用户困惑，所以实践中也应该保持递增。
💡 最常见的新手错误：更新了 versionName 但忘记递增 versionCode，导致 Play 拒绝上传，报错「Version code X has already been used」。
📐 Flutter 项目的版本号写法
Flutter 在 pubspec.yaml 中用一行统一管理：
version: 6.5.20+665200520

6.5.20 → versionName（用户可见）
665200520 → versionCode（Play 用来判断新旧）

+ 号前是 versionName，后是 versionCode。也可以在打包命令中覆盖：
flutter build appbundle --build-name=6.5.21 --build-number=665200521
🏷️ 多 Flavor 下的版本号策略
多马甲场景下，两个维度可以独立管理：

versionCode 全局共享：所有 flavor 用同一个 versionCode（来自 pubspec.yaml），每次统一递增。好处是维护简单，不容易漏更新某个马甲。

versionName 各 flavor 独立：在 build.gradle 的 productFlavors 中为每个 flavor 单独指定 versionName，反映各马甲自己的迭代节奏。这样 juscall 可以是 6.x，新马甲 call360 可以从 1.0.0 开始，互不影响。
  • versionCode 必须是正整数，且每次发布严格递增
  • 同一个 App（相同 applicationId）的 versionCode 不能重复上传
  • 不同 flavor（不同 applicationId）的 versionCode 互相独立，可以相同
  • iOS 对应字段：CFBundleShortVersionString（versionName）和 CFBundleVersion（versionCode）
  • Play 的「内部测试」轨道允许重复上传相同 versionCode，方便调试
  • versionCode 编码技巧：把版本信息编入数字，方便排查（见下方本项目示例）
📌 本项目示例
pubspec.yaml：version: 6.5.20+665200520
versionCode 665200520 的含义可拆解为：6-65-20-0520，将主版本、次版本、修订号、日期编入数字中，一眼能看出这个包是什么版本打的。

各 flavor 的 versionName（build.gradle 中独立配置）：
  • juscall：未单独设置，继承 pubspec.yaml 的 6.5.20
  • duovoice / truetalk：4.5.20（成熟马甲，版本较高）
  • duocall / anycall：2.5.20（中期马甲）
  • call360：1.0.0（新马甲，从 1.0 起步）

所有马甲共用同一个 versionCode（665200520），每次打包统一在 pubspec.yaml 中递增，避免漏更新某个马甲。

代码混淆 — ProGuard / R8

Release 包自动开启；混淆规则写错会导致 App 启动崩溃
📖 缩减代码文档 📋 ProGuard 规则
Android Release 包在 build.gradle 中开启 minifyEnabled true 后，构建工具（R8，ProGuard 的继任者）会做三件事：

① 压缩（Shrink）：删除未被调用的类、方法、字段，减小包体积。
② 混淆（Obfuscate）：将类名、方法名替换成无意义的短名称（如 a.b.c），增加反编译难度，保护商业逻辑。
③ 优化（Optimize）：内联方法、简化代码，提升运行效率。

常见问题：混淆会把第三方 SDK 需要的类名也改掉，导致 SDK 通过反射找不到类而崩溃。解决方法是在 proguard-rules.pro 中添加 -keep 规则，告诉 R8 哪些类不能被混淆。
💡 最高频的坑：Debug 包正常，Release 包崩溃——90% 是 proguard 规则缺失导致的。每接入一个新 SDK，必须检查它是否提供了对应的 proguard 规则。
  • minifyEnabled true：开启 R8 压缩 + 混淆 + 优化
  • shrinkResources true：同时删除未引用的资源文件（图片、layout 等）
  • -keep class com.example.** { *; }：保留指定包下所有类不被混淆
  • -keepattributes *Annotation*：保留注解信息（Retrofit 等依赖注解的库必须加）
  • 多数 SDK 在文档或 AAR 内自带 consumer-rules.pro，会自动合并，不用手动添加
  • 崩溃堆栈是混淆后的短名称，需用 retrace 工具还原（Crashlytics 自动还原）
📌 本项目示例
本项目 build.gradle 中 release 构建配置：
minifyEnabled true / shrinkResources true / proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'

proguard-rules.pro 中需要为 JC 通话 SDK、TradPlus、AppLovin、Firebase、Realm 等各自添加 keep 规则。各 SDK 官方文档的「混淆」章节会提供对应规则，接入新 SDK 后应第一时间检查并补充。

验证方式：每次新接入 SDK 后，必须打一次 Release 包在真机上完整走一遍功能，不能只依赖 Debug 包测试。

证书（Certificate）& 描述文件（Provisioning Profile）

iOS 签名体系：比 Android Keystore 更复杂，分「证书」和「描述文件」两层
📖 代码签名文档 🔑 证书管理
iOS 签名分两层：

① Certificate（证书）：证明「你是谁」。分开发证书（Development）和发布证书（Distribution）。证书绑定到开发者账号，用私钥签名。

② Provisioning Profile（描述文件）：证明「这个 App 被允许安装在哪些设备上」。它把 Certificate + Bundle ID + 设备 UDID 三者绑定在一起。

构建 iOS 包时，Xcode 同时用这两个文件对 App 签名。
💡 Android 只有 Keystore 一层，iOS 有两层，这是新手最容易混淆的地方。
  • Development Profile：开发/调试用，只能装到授权设备
  • Distribution Profile：发布用，App Store 或企业分发
  • Bundle ID：iOS 的「包名」，全局唯一，如 com.example.myapp
  • 证书有效期 1 年，到期需重新生成并更新描述文件
  • 描述文件包含允许安装的设备 UDID 列表（开发版）
  • Xcode 可自动管理签名（Automatically manage signing）
Android vs iOS 签名对比
Android：justalk.keystore（一个文件搞定，自己保管）
iOS：Distribution Certificate（证明身份）+ App Store Provisioning Profile（证明权限）需配合使用，且每年过期。

Sign in with Apple — iOS 强制要求的登录方式

App 提供第三方登录（如 Google 登录）时，苹果强制要求同时支持 Apple 登录
📖 Apple 登录文档 🎯 Flutter 插件
Apple 规定：如果 App 使用了任何第三方账号登录（Google、Facebook、微信等），则必须同时提供「Sign in with Apple」选项，否则审核会被拒绝。

💡 这条规定是很多 Android 优先的团队在移植到 iOS 时被审核打回的常见原因之一。
  • App 有第三方登录 → 必须有 Apple 登录，无例外
  • 需要在 Apple Developer 后台开启 Sign in with Apple 能力（Capability）
  • Flutter 可用 the_apple_sign_in 插件接入
  • 用户可选择隐藏邮箱，后端需能处理中继邮箱
  • Token 验证需在服务端调用 Apple 的 API，不能只做客户端验证
  • Android 不受此规定约束，可只有 Google 登录

Firebase — Google 的移动端后端平台（BaaS）

提供登录、数据库、推送、崩溃监控等一站式后端能力，无需自建服务器
📖 Firebase 文档 🌐 控制台
Firebase 是 Google 提供的后端即服务（BaaS）平台。开发者不需要自己搭服务器，就可以直接使用登录认证、实时数据库、云函数、文件存储等功能。接入方式是将 google-services.json（Android）放入项目，SDK 自动连接到对应 Firebase 项目。
💡 为什么需要：快速获得用户认证、远程配置下发、崩溃日志收集等能力，且每个马甲建一个独立项目，数据完全隔离。
  • Authentication：用户登录（手机号、Google、Apple）
  • Remote Config：远程下发配置（如服务器地址），无需发版
  • Dynamic Links：智能跳转链接（区分已装/未装 App）
  • Crashlytics：崩溃收集与分析
  • google-services.json：App 的身份证，含项目 ID、API Key、合法 SHA1 白名单
  • SHA-1 必须添加到 Firebase，Google 登录才能正常工作
🗝️ google-services.json 是什么 & 为什么要更新两次
它是什么：Firebase 给 App 的"身份证 + 通行令牌"。App 启动时 Firebase SDK 读取它，知道「连哪个 Firebase 项目」以及「哪些签名的 App 被允许使用 Google 登录」。文件里的 certificate_hash 字段就是已注册的 SHA1 白名单。

为什么要更新两次：整个流程中会产生 3 个 SHA1，需要分两次加入：

第一次下载（上传 Play 之前）
  ✅ debug keystore SHA1  ← 让开发者本地调试时 Google 登录可用
  ✅ release keystore SHA1  ← 让 release 包可以使用 Google 登录

用 release 包上传到 Google Play
  → Play 生成自己的「Play App Signing」密钥（第 3 个 SHA1）

第二次下载（获取 Play SHA1 后）
  ✅ debug keystore SHA1  ← 不变
  ✅ release keystore SHA1  ← 不变
  ✅ Play App Signing SHA1  ← 新增！用户从商店下载的正式版靠它登录

为什么 Play 会有自己的签名：开启「Play App Signing」后，Google 会将你上传的 AAB 用 Play 自己的密钥重新签名再分发给用户，这样即使你的 release keystore 丢失，也不影响 App 更新。但这也意味着用户设备上安装的 App 签名是 Play 的密钥，而不是你的 keystore——所以 Firebase 必须也注册这个 SHA1，Google 登录才能通过验证。
📌 本项目示例
每个马甲对应独立 Firebase 项目：call360 → Firebase 项目 call360-4a9be。 google-services.json 放在 android/app/src/call360/ 目录下，Gradle 构建时自动选用对应马甲的配置文件。 查看 call360 的 google-services.json，可以看到 oauth_client 数组里有 2 条 certificate_hash 记录，分别对应 debug 和 release/Play 的 SHA1。 Remote Config 按国家（Egypt / Qatar / India）配置不同的 routerUrl，App 启动时动态拉取。

推送通知 — FCM（Android）& APNs（iOS）

App 不在前台时也能主动触达用户；Android 和 iOS 底层机制完全不同
📖 FCM 文档 🍎 APNs 文档 🎯 Flutter 插件
推送通知让服务器在任意时刻向用户设备发送消息，即使 App 已被关闭。两个平台的底层通道完全不同：

Android — FCM（Firebase Cloud Messaging）
消息由你的服务器发给 FCM，FCM 再转发到用户设备。App 需要在 Firebase 项目中开启 Cloud Messaging，设备启动时会向 FCM 注册并获得一个唯一的 Device Token，服务端靠这个 Token 定向推送。

iOS — APNs（Apple Push Notification service）
消息必须先经过苹果的 APNs 服务器中转，再到达用户设备。你的服务器要用苹果颁发的 APNs 证书（或 APNs Key）向 APNs 发请求。FCM 也可以作为 iOS 推送的中间层（服务端只对接 FCM，FCM 内部再转发给 APNs），简化服务端实现。
💡 核心区别：Android 推送走 Google 通道，在国内受限（需要厂商通道替代）；iOS 推送必须经过 APNs，苹果强管控，但国内外都能用。
  • Device Token：设备在推送服务注册后获得的唯一 ID，服务端存储后用于定向推送
  • Topic / 广播：订阅某个主题，服务端向主题推送可触达所有订阅设备
  • 前台通知：App 在前台时默认不显示通知栏，需额外处理
  • 后台通知：App 被杀死时仍可收到，需申请后台权限
  • 通知权限：iOS 必须弹窗请求用户授权；Android 13+ 同样需要请求权限
  • 国内 Android 推送需接入厂商通道（小米、华为、OPPO 等）绕过 GMS 限制
📡 推送链路对比
Android：你的服务器 → FCM 服务器 → 用户 Android 设备
iOS（直接）：你的服务器（带 APNs 证书）→ APNs 服务器 → 用户 iPhone
iOS（经由 FCM）：你的服务器 → FCM 服务器 → APNs 服务器 → 用户 iPhone
使用 FCM 统一管理 Android + iOS 推送是最常见的做法，服务端只需对接一个 API。
🔑 iOS 推送的额外配置
iOS 推送必须在 Apple Developer 后台开启 Push Notifications Capability（推送能力），并上传一个：
  • APNs 证书（.p12）：有效期 1 年，到期需续期
  • 或 APNs Key（.p8）：不过期，推荐使用

这个证书/Key 需要发给后端，后端用它与 APNs 服务器建立信任连接。如果用 FCM 统一管理，则将 APNs Key 上传到 Firebase 控制台即可，后端只需对接 FCM API。
📌 本项目示例
本项目在 iOS 的 Runner.entitlements 中声明了 aps-environment: development，表示当前配置的是开发环境推送通道。正式发布时需将其改为 production，并在 Provisioning Profile 中启用 Push Notifications 能力。

Android 端通过 firebase_messaging Flutter 插件接入 FCM，App 首次启动时获取 Device Token 并上报给业务服务器，服务器在需要时通过 FCM API 发送通话提醒、消息通知等推送。

隐私政策 & 用户协议 — 上架硬性要求

Google Play 和 App Store 都强制要求提供隐私政策链接，缺少会被拒绝上架
📖 Play 隐私要求 🍎 Apple 隐私指南
无论 App 大小，只要收集了任何用户数据（账号、手机号、设备 ID、位置等），就必须提供一个公开可访问的隐私政策页面，并在 Play Console / App Store Connect 的商店配置中填入链接。

隐私政策需要说明：收集了哪些数据、为什么收集、是否分享给第三方、用户如何删除账号/数据。用户协议（Terms of Service）不是强制要求，但涉及付费功能时强烈建议同时提供。
💡 没有隐私政策链接 = 直接被拒审核，这是最容易被忽视的硬性要求之一。
  • 隐私政策必须托管在可公开访问的 URL，不能是 PDF 附件
  • 内容必须与 App 实际收集的数据一致，不能照抄模板而不修改
  • Play Console 要求在商店详情页和 App 内都能访问隐私政策
  • 用户必须在注册前能看到隐私政策（不能注册后才显示）
  • 涉及儿童用户须额外遵守 COPPA（美国）/ GDPR-K（欧盟）
  • 账号删除功能：Google Play 要求 App 提供账号删除入口（2024年起强制）
📌 本项目示例
本项目各马甲的隐私政策页面托管在各自域名下，如 call360 对应 call360.mmcallsapp.com/privacy。 在 product_string.dart 的 Call360LocalStrings 中有 privacyUrl 字段指向该地址，App 内的「隐私政策」按钮直接跳转。 Play Console 商店配置的隐私政策链接填入相同 URL。

应用商店审核 & 政策合规

提交前必须了解：哪些内容会被拒，哪些敏感权限需要额外说明
📖 Play 政策中心 🍎 App Store 审核指南
两个平台都有人工 + 机器审核，提交后不是立刻上线：

Google Play：通常 1–3 天，机器审核为主，人工复查高风险 App。审核通过后可自动或手动发布。被拒后可修改后重新提交，无次数限制。

App Store：通常 1–3 天，人工审核为主，更严格。被拒后有申诉渠道（Resolution Center）。连续被拒或违反重大政策可能导致开发者账号被封。
💡 VoIP 类 App（本项目类型）属于高审核风险类别，Play 和 Apple 都对通话录音、联系人权限、后台运行有额外审查。
⚠️ 常见被拒原因
敏感权限未说明：申请了 READ_CONTACTS / CALL_LOG / 录音权限，但没有在商店说明用途
隐私政策缺失或链接失效：最常见，提交前务必检查链接可访问
截图与实际功能不符：商店截图展示了 App 没有的功能
内购商品未配置：代码里有内购逻辑，但 Play / ASC 后台没有创建对应商品
iOS：缺少 Sign in with Apple：有 Google 登录但没有 Apple 登录
iOS：后台模式未声明：App 在后台保持通话连接，但 Info.plist 没有声明 VoIP 后台模式
  • Play 新账号前几次上传审核较慢（可能 7 天以上），属正常现象
  • 敏感权限（位置、录音、联系人）需在 App 内使用时才请求，不能启动就全部申请
  • 截图必须使用真实设备截图，不能只用设计稿
  • 分级（内容分级问卷）：Play 要求填写 IARC 分级问卷，涉及暴力/成人内容的会限制受众
  • App Store 被拒后可在 Resolution Center 与苹果审核员文字沟通说明情况
  • 重大政策违规（欺诈、恶意代码）可能导致账号封禁且无法申诉

CI/CD 自动化
把繁琐的手动打包流程变成一条命令，多马甲项目尤其必要
🤖

为什么多马甲项目特别需要 CI/CD

手动打包 12 个马甲：重复操作多、容易漏步骤、人为失误风险高
📖 GitHub Actions 🚀 Fastlane ☁️ Codemagic
CI/CD（持续集成 / 持续交付）把「代码提交 → 构建 → 测试 → 打包 → 上传」的流程自动化。对于多马甲项目，每次发版都需要对多个 flavor 重复相同步骤，手动操作极易出错。

CI（Continuous Integration）：代码推送后自动构建和测试，及早发现问题
CD（Continuous Delivery）：自动打包并上传到 Play Console / App Store Connect，甚至自动发布
💡 多马甲项目的 CD 价值尤其大：一次配置，之后每个马甲的打包上传都能一键完成，不再需要开发者手动重复操作。
😓 当前手动打包需要做的事（以 iOS 为例）
① 切换到正式 credential（sed 修改 pubspec.yaml 中的 git 仓库地址）
② 注释掉其他马甲的 assets，只保留当前马甲的资源
③ flutter pub get → pod install → 运行 fix_jcmanager_prefix.sh
④ Xcode 选对 Scheme 和 Build Configuration，执行 Archive
⑤ Organizer 上传到 App Store Connect
⑥ 打包完成后恢复 pubspec.yaml 的改动（credential 和 assets）
⑦ 对下一个马甲重复以上步骤

换成 CI/CD 后：触发一次流水线，脚本自动按顺序完成所有步骤，开发者只需等待结果通知。
🚀

Fastlane — 移动端打包自动化首选工具

用 Ruby DSL 描述打包流程，同时支持 Android 和 iOS，与各大 CI 平台集成
📖 Android 接入 🍎 iOS 接入 📦 supply（上传 Play）
Fastlane 是专为移动端设计的自动化工具，核心概念是 lane（泳道）：每个 lane 是一系列 action 的组合，如「构建 → 上传 → 发通知」。写在 Fastfile 中，像写脚本一样描述流程。

常用 action：
  • gradle：调用 Android Gradle 构建 APK/AAB
  • supply：上传 AAB 到 Google Play
  • gym：调用 xcodebuild 构建 iOS Archive
  • deliver：上传 IPA 到 App Store Connect
  • match：自动管理 iOS 证书和 Provisioning Profile（推荐）
💡 Fastlane match 是 iOS 证书管理的最佳实践：把证书统一存在私有 Git 仓库，团队成员和 CI 机器都从同一个地方拉取，避免「我本机能打，CI 打不了」的问题。
  • Fastfile 用 Ruby 语法，不需要会 Ruby，照葫芦画瓢即可
  • lane 可以有参数，如 fastlane android deploy flavor:call360
  • 内置 Slack / 钉钉通知 action，打包完成自动发消息
  • match 加密存储证书，用 git 管理，团队共享不混乱
  • pilot（TestFlight 上传）和 supply（Play 上传）都有增量上传能力
  • 可在本地运行，也可挂到 GitHub Actions / GitLab CI 等平台
Fastfile 示例（Android 多 Flavor）
lane :deploy_android do |options|
  flavor = options[:flavor]
  gradle(task: "bundle", flavor: flavor, build_type: "Release")
  supply(track: "internal", aab: "app/build/outputs/bundle/#{flavor}Release/app-#{flavor}-release.aab")
end

CI 平台 — GitHub Actions / GitLab CI / Codemagic

提供运行 Fastlane 的云端机器，代码推送自动触发构建
📖 GitHub Actions 🦊 GitLab CI ☁️ Codemagic Flutter
CI 平台提供云端的虚拟机（Runner），在代码推送或手动触发时自动运行构建脚本。不同平台特点：

GitHub Actions：与 GitHub 仓库无缝集成，免费额度每月 2000 分钟，macOS Runner 较贵，但生态最成熟。

GitLab CI：本项目使用 GitLab 托管代码，GitLab CI 与仓库天然集成，可以用自托管 Runner（自己的 Mac mini）降低成本。

Codemagic：专为 Flutter 设计，配置最简单，内置 Flutter 环境，对 Flutter 多 flavor 支持开箱即用，按分钟计费。

GitHub Actions：生态最好，公共仓库免费，私有仓库有限额，macOS 贵
GitLab CI：与本项目 GitLab 仓库直接集成，自建 Runner 成本低
Codemagic：Flutter 专属，配置最少，不用写 YAML，按使用付费
自建 Jenkins + Mac mini：成本最低（硬件一次性投入），适合打包频繁的团队

  • iOS 构建必须在 macOS Runner 上，是 CI 成本的主要来源

  • 产物（Artifact）：构建好的 AAB/IPA 可上传为 CI 产物，方便下载
  • 本项目用 GitLab 托管，最直接的选择是 GitLab CI + 自建 macOS Runner

CI 环境中的凭证安全管理

Keystore、证书、API Key 绝不能提交到 git，统一用 CI Secrets 注入
📖 GitHub Secrets 🦊 GitLab CI Variables
CI 构建需要用到很多敏感信息：Android Keystore 文件 + 密码、iOS 证书 + 描述文件、Google Play 服务账号 JSON、App Store Connect API Key 等。这些绝对不能提交到 git 仓库（即使是私有仓库）。

标准做法：将敏感信息存储在 CI 平台的 Secrets / CI Variables 中，构建时作为环境变量注入，或将二进制文件（Keystore、证书）Base64 编码后存为 Secret，CI 脚本解码后使用。
💡 本项目的 credential（包含 jcAppKey 等加密密钥）已通过私有 git 仓库（credential.git）隔离。但 Keystore 文件和密码也需要同样处理，不能直接存在业务仓库中。

Android
  • justalk.keystore / juscall.keystore 文件（Base64 编码存 Secret）
  • key.properties 中的 storePassword / keyPassword
  • Google Play 服务账号 JSON（用于 Fastlane supply 上传）

iOS
  • Distribution Certificate（.p12 + 密码）
  • Provisioning Profiles（JusCall App Store、DuoVoice App Store）
  • App Store Connect API Key（用于 Fastlane deliver 上传）

通用
  • SSH Key（用于拉取私有 git 仓库：credential.git、jcmanager.git 等）

三种持久化方案 — SharedPreferences / SQLite / Realm

按数据复杂度选型：键值对用 SharedPreferences，结构化数据用 SQLite 或 Realm
📖 SharedPreferences 🗄️ sqflite 🔵 Realm Flutter
App 内的数据持久化有三个层次，从简单到复杂：

① SharedPreferences（键值对）
存储少量简单数据，如用户设置、登录 Token、开关状态。底层是 XML 文件（Android）/ NSUserDefaults（iOS）。读写简单，不支持查询。

② SQLite（关系型数据库）
存储有结构的数据，支持 SQL 查询、联表、事务。Flutter 用 sqflite 插件接入。适合通讯录、消息记录、账单等表格型数据。

③ Realm（对象型数据库）
由 MongoDB 出品的移动端专用数据库。直接存储 Dart 对象，不需要写 SQL，性能比 SQLite 更高，支持实时监听数据变化（reactive）。适合数据量大、查询复杂、需要实时同步的场景。
💡 选型原则：登录态/配置 → SharedPreferences；通讯录/本地消息 → SQLite 或 Realm；需要离线优先 + 云同步 → Realm（可接 MongoDB Atlas 实现云端同步）。
📊 三种方案对比
SharedPreferences SQLite (sqflite) Realm
数据结构 Key-Value 表 / 行 / 列 对象
查询能力 ❌ 无 ✅ SQL ✅ Realm Query
性能 快（内存缓存） 中等 快（零拷贝）
典型用途 Token、设置 消息、账单 通讯录、大量结构化数据
📌 本项目示例
本项目同时用了三种方案：

SharedPreferences（shared_preferences: ^2.5.3）：存储用户登录状态、本地设置项（语言、通知开关）、缓存的 Remote Config 值等轻量数据。

sqflite（sqflite: ^2.4.1）：存储本地消息记录、通话记录（Recents）、缓存的联系人数据，支持按时间范围查询、分页加载。

Realm（realm: ^20.2.0）：存储需要实时响应 UI 变化的结构化数据，Realm 的 RealmResults 支持监听器，数据变化时自动触发 UI 刷新，无需手动通知。

Logcat & 原生层调试

Flutter DevTools 看不到原生层日志；Logcat 是 Android 崩溃和原生插件调试的主要手段
📖 Logcat 文档 🐛 Android 调试
Flutter App 实际上分两层运行：上层是 Dart 代码（Flutter），下层是原生 Android/iOS 代码（Java/Kotlin/OC/Swift）。Flutter DevTools 只能看到 Dart 层的日志，原生层的日志必须用平台工具查看：

Android — Logcat：Android Studio 底部的 Logcat 面板，或命令行 adb logcat。所有原生代码的 Log.d()、系统崩溃堆栈、广告 SDK 日志都在这里。

iOS — Console / Xcode：Xcode 底部的调试控制台，或 macOS 的 Console.app。
💡 「Flutter 层没报错但功能不正常」时，多半是原生插件出了问题——先去 Logcat 看有没有 Exception 或 ERROR 级别的日志。
  • Logcat 过滤器：输入包名或 Tag 过滤，避免日志太多看不到关键信息
  • adb logcat -c：清空 Logcat 缓存，方便复现特定问题
  • adb install app-debug.apk：命令行安装调试包到真机
  • adb shell dumpsys activity：查看当前 Activity 栈
  • Firebase Crashlytics：线上崩溃自动上报，可在控制台查看完整堆栈
  • 广告 SDK 问题：先在 Logcat 过滤 Tag（如 TradPlus、Admob）查看初始化日志
📌 本项目调试经验
本项目开发 call360 马甲时，出现 JCClient app key cannot be empty! 崩溃。这个错误来自原生 JC SDK（Java 层），Flutter DevTools 看不到，需要在 Logcat 中搜索 JCClient 才能看到完整报错，进而定位到是 credential 插件缺少 call360 的 key 映射。

Flutter 测试体系 — 单元 / Widget / 集成测试

三个层次的测试覆盖不同范围，从函数级到完整用户流程
📖 Flutter 测试文档 🔬 单元测试 🖼️ Widget 测试
Flutter 测试分三个层次：

① 单元测试（Unit Test）：测试单个函数或类的逻辑，不需要设备，运行最快。适合测试工具函数、数据解析、业务逻辑。

② Widget 测试（Widget Test）：在虚拟环境中渲染 Widget，验证 UI 的展示和交互逻辑，不需要真机，比集成测试快。

③ 集成测试（Integration Test）：在真机或模拟器上运行完整的用户操作流程，如「点击登录按钮 → 输入手机号 → 验证跳转到首页」，最接近真实场景但最慢。
💡 移动端实践中，单元测试性价比最高——覆盖核心业务逻辑（如版本号解析、数据格式转换），防止重构时引入 regression。Widget 测试和集成测试成本较高，一般只覆盖关键流程。
  • 测试文件放在 test/ 目录，命名以 _test.dart 结尾
  • 运行全部测试：flutter test
  • 单元测试用 test() 函数，断言用 expect()
  • Widget 测试用 testWidgets()，通过 WidgetTester 模拟点击/输入
  • Mock：用 mockito 包模拟网络请求、数据库等外部依赖
  • CI 中加入 flutter test 步骤，push 代码自动跑测试，不通过则阻断构建
📌 单元测试示例（测试版本号解析逻辑）
test('versionCode 应大于上一版本', () {
  final current = 665200520;
  final previous = 665150312;
  expect(current > previous, isTrue);
});
